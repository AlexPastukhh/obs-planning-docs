Пока не выполняй саму работу глубже, чем необходимо для корректной постановки, планирования и проверки готовности.\n\n[[module:core.context-interpretation]]\n[[module:core.need-proposal-semantics]]\n[[module:core.scenario-realization]]\n[[module:core.finding-model]]\n[[module:core.finding-explanation]]\n[[module:core.decision-governance]]\n[[module:core.proposal-composition]]\n[[module:core.user-assistance]]\n[[module:prework.wr-ea-semantics]]\n\n## 1. Target / Scope\n\nОпредели конкретную единицу работы и текущий узел планирования. Если она является SRU или под-SRU, укажи её parent path и вклад в Desired Scenario. Если Scenario/SRU модель для задачи неуместна, не навязывай её.\n\n## 2. User Intent / Semantic Foundation\n\nВосстанови:\n- User Needs `N-*`;\n- Fundamental Requirements `FR-*`;\n- уже committed decisions/constraints;\n- существующий Desired Scenario и SRU composition, если они уже есть;\n- user-origin Proposals, которые ещё не committed;\n- существенные assumptions и Evidence Gaps.\n\nНе повышай пользовательский Proposal до Requirement только из-за происхождения.\n\n## 3. Task Framing / Scenario Fit\n\nПроверь, ведёт ли сама единица работы к нужному outcome и является ли её место в Scenario/SRU tree обоснованным. Отдельно ищи upstream Problems/Risks/Decision Uncertainties/Improvement Opportunities: возможно, parent SRU, состав реализации, Scenario или scope можно/нужно изменить до дорогой downstream работы.\n\nЕсли существует более маленькая validation/staged версия, способная быстро дать информацию и потенциально изменить дальнейший план, вынеси её как Proposal с соответствующим User Review Priority.\n\n## 4. Candidate Work Requirements\n\nСформируй атомарные `WR-*` именно к этой единице работы. Для каждого укажи requirement, provenance, связь с N/FR/Scenario/SRU/committed decision и verification criterion. WR, зависящий от `PR-*`, явно пометь как conditional on that Proposal.\n\n## 5. Candidate Error Axes\n\nСформируй существенные `EA-*`: механизм → условия → наблюдаемое нежелательное следствие → verification. Не создавай axes ради количества. При наличии material Risk связывай EA с canonical `F-R-*` вместо дублирования.\n\n## 6. Findings / Upstream Feedback\n\nСобери найденные при планировании `F-P/F-R/F-U/F-O`. Для каждого material finding укажи CURRENT/UPSTREAM, semantic target, concrete explanation, User Review Priority и связанные Proposals. Особенно явно покажи upstream findings, которые способны изменить Scenario, parent SRU, scope, costs или сделать downstream работу ненужной.\n\n## 7. Proposals / Candidate Composition\n\nСоздай один или несколько `PR-*` для всех существенных ещё не принятых решений. Покажи relations/groups и Recommended Candidate Composition. Никакой Proposal, включая `origin:user`, не считается committed до commit всей согласованной композиции.\n\n## 8. Completeness / Readiness\n\nПеред завершением проверь:\n- достаточно ли WR для цели этой единицы;\n- покрывают ли EA основные правдоподобные способы провала;\n- сохраняет ли SRU ожидаемый вклад в Scenario;\n- не добавляется ли преждевременная сложность;\n- нет ли более дешёвого staged/validation пути;\n- покрыты ли обязательные N/FR;\n- нет ли conflicts/unsatisfied `REQUIRES`;\n- нет ли blocking upstream finding или пользовательской зависимости.\n\nОпредели readiness: `READY FOR COMMIT / READY WITH EXPLICIT ASSUMPTION / PARTIALLY BLOCKED / NOT READY`.\n\n## 9. Candidate Execution Plan\n\nСформируй краткий кандидатный plan реализации, покрывающий WR и учитывающий EA, SRU decomposition, dependencies и выбранные Proposals. Разделяй независимые и blocked части. Предпочитай самый простой достаточный путь, не ухудшающий Scenario/FR.\n\n## 10. Candidate Verification Plan\n\nУкажи, как будут проверены WR, EA, ключевые assumptions, material Risks и вклад SRU в Scenario. Для staged версии укажи, какое новое знание должно быть получено перед следующим investment/commit.\n\n## 11. Transaction Output\n\nПокажи:\n1. Target и parent/context;\n2. User Needs / Fundamental Requirements;\n3. Desired Scenario / SRU context, если применимо;\n4. Candidate WR;\n5. Candidate EA;\n6. Findings с CURRENT/UPSTREAM и User Review Priority;\n7. User Assistance / Evidence Gaps;\n8. material questions / Decision Uncertainties с blocking status и affected scope;\n9. Proposals / Groups / Relations;\n10. Recommended Candidate Composition и существенные alternatives;\n11. Execution Plan;\n12. Verification Plan;\n13. readiness;\n14. `Transaction Status: OPEN / READY FOR COMMIT / BLOCKED`.\n\n**Не называй это committed baseline.** Только после явного атомарного принятия всей согласованной композиции зафиксируй её как `BASELINE COMMITTED`, сохранив различие между исходными committed inputs, Proposals и итоговыми committed decisions.",
