Target / Scope\n\nОпредели объект и границы проверки из моего явного указания и релевантного контекста. Если объект неоднозначен, не выбирай последний автоматически.\n\n## 2. Task / Scenario Reconstruction\n\nВосстанови исходную задачу, User Need, применимые FR/requirements/constraints и критерии успеха. Если уместно, восстанови Desired Scenario и место проверяемой работы в SRU tree. Не переопределяй задачу без основания и не придумывай неизвестный процесс выполнения.\n\n## 3. Independent Re-check\n\nПроведи независимую перепроверку ключевых и наиболее рискованных частей. Сравни собственный обоснованный результат с проверяемым только после независимой реконструкции/проверки.\n\n## 4. Findings Search\n\nИщи и классифицируй:\n- `F-P-*` Problems;\n- `F-R-*` Risks;\n- `F-U-*` Decision Uncertainties;\n- `F-O-*` Improvement Opportunities.\n\nОтдельно фиксируй Evidence Gaps / Review Limitations. Не смешивай Opportunity с defect и Risk с подтверждённой Problem.\n\nДля каждого material finding покажи concrete scenario/reproduction и связь с Need/FR/requirement/Scenario. Укажи semantic target и CURRENT/UPSTREAM.\n\n## 5. Upstream / Realization Impact\n\nОсобенно ищи findings, обнаруженные в текущей реализации, но относящиеся к parent SRU, составу SRU, Desired Scenario, Need/FR или стратегии staged/full realization. Такие findings имеют повышенный User Review Priority. Не маскируй их локальным техническим исправлением.\n\nОценивай не только итоговый outcome, но и стоимость пути: время, усилия, деньги, ручные шаги, maintainability, accumulated complexity и option value, если применимо.\n\n## 6. Questions / Proposals\n\nQuestions привязывай к конкретным findings или Proposal decisions. Для каждого material изменения/исправления сформируй один или несколько `PR-*`; proposal review не является автоматически принятым решением. Укажи User Review Priority и Decision Autonomy. Покажи relations/groups, если варианты связаны или взаимоисключаются.\n\n## 7. User Assistance\n\nЗапрашивай только минимально необходимое пользовательское действие, когда оно существенно лучше автономного обхода. Продолжай независимые незаблокированные части.\n\n## 8. Disposition / Deferred\n\nДля findings, не требующих действия сейчас, используй `disposition: deferred` с причиной и revisit trigger. Не создавай отдельную природу `Deferred` и не демотируй реальную Problem ради завершения.\n\n## 9. Review Output\n\nРаздели результат на:\n1. Findings — Problems / Risks / Decision Uncertainties / Improvement Opportunities;\n2. Upstream Findings (cross-reference к canonical records);\n3. что выдержало независимую проверку;\n4. Evidence Gaps / Review Limitations;\n5. User Assistance;\n6. deferred/resolved/other dispositions;\n7. Proposals / Proposal Groups и unresolved decisions с `blocking / non-blocking / partially blocking`;\n8. Recommended Remediation Candidate Composition, если несколько remediation/improvement Proposals нужно оценивать совместно.\n\nЕсли существенных Problems нет, скажи это прямо. Это не означает отсутствия Risks/Uncertainties/Opportunities.\n\n## 10. Review Log\n\nСформируй Review Log по общему contract и сохрани его только при реально подтверждаемой записи. В Log должны быть видны canonical findings, upstreamness, dispositions, существенные Proposals и ограничения проверки.",
