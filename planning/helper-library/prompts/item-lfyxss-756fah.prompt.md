  "text": "Независимо и критически перепроверь указанное мной review как объект проверки: корректность его findings, полноту, классификацию, доказательность, proposals и соблюдение review-protocol.\n\n[[module:review.verification-axes]]\n[[module:core.context-interpretation]]\n[[module:core.need-proposal-semantics]]\n[[module:core.scenario-realization]]\n[[module:core.finding-model]]\n[[module:core.finding-explanation]]\n[[module:core.decision-governance]]\n[[module:core.proposal-composition]]\n[[module:core.user-assistance]]\n[[module:review.independent-verification]]\n[[module:review.record-semantics]]\n[[module:review.meta-review-consolidation]]\n[[module:prework.wr-ea-semantics]]\n\n**Порядок проверки:** после восстановления target/scope сначала явно выведи предварительные общие, ситуационные и (при необходимости) мета-оси; затем проверяй и дополняй их. В конце сопоставь material оси с фактическими доказательствами и назови непроверенное. Не считай готовый список полным автоматически.\n\n## 1. Target Review / Underlying Context\n\nОпредели конкретное review, его target/version/scope, исходную задачу и доступный review-prompt/protocol. Не проверяй другой более новый review только из-за свежести.\n\n## 2. Review Identity / Lineage\n\nСохраняй IDs сущностей проверяемого review неизменными как source references. Новые findings самого meta-review не смешивай с ними: используй `MR-F-P/MR-F-R/MR-F-U/MR-F-O`, а новые Proposals meta-review — `MR-PR-*`. Явно показывай, какая запись принадлежит исходному review, а какая возникла только при meta-review.\n\n### Исходный материал и файл meta-review\n\nПо умолчанию опубликованный результат meta-review должен быть **отдельным Markdown-документом**, а не заменой исходного review. В начале укажи оригинал, target/version, его link/commit или достоверное ограничение доступа и scope перепроверки. Для существенных `F-*/PR-*` исходного review зафиксируй статус проверки: подтвердилось / слишком сильное утверждение / false positive / непроверено; для false negatives добавь новые `MR-F-*`. Собственные findings и `MR-PR-*` держи отдельно, с явными ссылками на исходные ID.\n\nЕсли полное исходное review существует только в текущем чате и доступно целиком, при публикации meta-review сохрани также отдельный source snapshot в `forfiles` без смыслового редактирования. Если оригинал уже опубликован или находится в согласованном хранилище, просто ссылайся на него; **дубликат не требуется**. Если оригинал доступен лишь частично, не утверждай, что его полный файл сохранён. Публикуй meta-review и, при обоснованных изменениях, отдельное полное Revised Final Review согласно `review.final-review-lineage` и `output.situational-github-artifacts`, сохраняя исходный review без перезаписи.\n\n## 3. Independent Verification\n\nНезависимо проверь ключевые утверждения review и исходный объект в достаточной степени, чтобы оценить false positives, false negatives и severity. Не доверяй review только потому, что оно выглядит подробным.\n\n### Scenario basis исходного ревью\n\nПроверь, опиралось ли исходное review на действующий Desired Scenario **или на сценарный путь, логически вытекающий из применимых требований**, даже когда этот путь не был оформлен отдельным документом. Отдели подтверждённое ожидание от `candidate/inferred` гипотезы; не повышай гипотезу до подтверждённой Problem. Если исходная проверка уже корректно покрыла эти переходы, не придумывай пропуск только из-за отсутствия файла `Scenario`. Новые собственные выводы оформляй `MR-F-*`, а исходные `F-*` оставляй source references.\n\n## 4. Review Axes / Meta-axes / Protocol Compliance\n\nВосстанови обязательные требования к проверяемому review из исходного review-prompt, пользовательских указаний и контекста. Проверяй не только качество присутствующих элементов, но и отсутствие обязательных.\n\nЕсли protocol требовал finding classification, concrete reproduction, WR/EA statuses, Review Log, proposals, User Review Priority/Decision Autonomy, blocking status, limitations или другое — проверь содержательное выполнение. Если исходный protocol недоступен, не угадывай: укажи, что нельзя надёжно проверить.\n\n## 5. Finding Classification / Explanation\n\nДля каждого существенного утверждения review проверь:\n- не названа ли Risk подтверждённой Problem;\n- не названа ли Opportunity defect;\n- не превращён ли Evidence Gap автоматически в Risk/Problem;\n- действительно ли Decision Uncertainty содержит материально разные варианты;\n- показана ли конкретная ситуация/reproduction там, где это применимо;\n- связана ли Problem с целью/requirement и expected behavior;\n- для material questions/decision forks указан ли корректный `blocking / non-blocking / partially blocking` и affected scope.\n\n## 6. Level / Upstream / Scenario Impact\n\nПроверь, правильно ли review определило semantic target и CURRENT/UPSTREAM. Ищи пропущенные upstream findings, способные изменить parent SRU, Scenario, Need/FR, scope, costs, maintainability, accumulated complexity или staged/full strategy.\n\nОтдельно проверь, не было ли локальное исправление предложено там, где сначала требовалось пересмотреть upstream decision.\n\n## 7. User Review Priority / Decision Autonomy\n\nПроверь обе оценки независимо. Высокий impact не равен автоматически отсутствию технической компетентности ИИ, а низкий impact не даёт автономии при неизвестном пользовательском preference. Убедись, что как минимум оценены Need, scope, radical complexity/cost, Scenario/process impact, reversibility, evidence и AI competence.\n\n## 8. Work Requirements / Error Axes\n\nЕсли review работало с baseline, проверь корректность WR statuses, EA interpretation и новых findings. `EA` не должна трактоваться как подтверждённый defect только из-за наличия в baseline.\n\n## 9. False Positives / False Negatives / Severity\n\nСоставь:\n- подтверждённые замечания review;\n- ошибочные/слишком сильные замечания;\n- пропущенные Problems/Risks/Uncertainties/Opportunities;\n- неверную severity/impact оценку;\n- Evidence Gaps review.\n\n## 10. Proposal / Composition Review\n\nПроверь, отделены ли findings от remediation Proposals; не был ли user-origin Proposal ошибочно повышен до Requirement; представлены ли реальные alternatives; корректны ли `REQUIRES/CONFLICTS/...`; не был ли отдельный selected Proposal выдан за committed composition.\n\nЕсли meta-review предлагает изменение, оно само является `MR-PR-*`, а не автоматически принятой правкой. При нескольких взаимозависимых вариантах собери Recommended Remediation Candidate Composition вместо списка независимых рекомендаций.\n\n## 11. User Assistance / Review Records\n\nПроверь, не пропустило ли review минимально полезный пользовательский input и не делегировало ли лишнее. Если Review Log был обязателен, проверь его полноту, canonical IDs, dispositions, limitations и правдивость заявления о persistence.\n\n## 11A. Revised Final Review / Change Impact Map\n\nПо `review.final-review-lineage` сформируй отдельную полную исправленную версию Final Review, если meta-review обосновывает изменения. Для каждого существенного `MR-F/MR-PR` отрази `applied / no change / unresolved / meta-only` с причиной; покажи обратную ссылку из новой итоговой записи на соответствующий раздел MR и прямую ссылку из MR на изменённый F/PR. Сохрани старую версию и самостоятельный meta-review. Не ограничивайся отдельным MR-документом или дельта-списком. При отсутствии реальных изменений явно оставь прежнее Final Review текущим.\n\n## 12. Meta-review Output\n\nПеред подробными разделами сформируй **краткий пользовательский результат** по `review.reader-overview` (он уже включён через `review.record-semantics`): 1–3 предложения с общей характеристикой исхода; самые важные `CRITICAL/HIGH` Findings и их Proposals рядом; краткое содержательное «Что в полном отчёте» по его фактическим заголовкам; следующий шаг. Если отчёт сохранён в файле, этот обзор обязателен **и в начале файла, и в ответе в чате до ссылки**. Не заставляй открывать файл, чтобы узнать общий итог. Не дублируй модуль прямой ссылкой.\n\n\nНачни с overall assessment и **наиболее важных подтверждённых выводов meta-review** с `CRITICAL`, затем `HIGH User Review Priority` независимо от категории ошибки. Каждый новый `MR-F-*` показывай сразу с относящимися к нему `MR-PR-*`: ID, действие, status, trade-offs, User Review Priority, Decision Autonomy и следующий шаг. Исходные `F-*/PR-*` показывай как source references, не присваивай их новым findings и не считай принятыми.\n\nЗатем содержательно отрази:\n1. Подтверждённые findings исходного review, false positives / overclaims и false negatives / omissions;\n2. protocol-compliance omissions, classification/explanation errors, level/upstream/Scenario-impact errors;\n3. User Review Priority / Decision Autonomy errors, Proposal/composition errors, Review Log / User Assistance errors;\n4. Новые canonical meta-review findings `MR-F-*` **с непосредственно связанными `MR-PR-*`**, сначала CRITICAL/HIGH, затем прочие. Не оставляй полноту PR-альтернатив только в отдельном списке;\n5. По необходимости отдельный краткий индекс новых Proposals / Groups и Recommended Remediation Candidate Composition (без дублирования независимых canonical записей).\n\nПоддерживай traceability между категориями ошибок и конкретными `MR-F-*`, а отсутствие ошибок в категории обозначай кратко, не создавая искусственных findings. Не исправляй проверяемый underlying project object молча; meta-review оценивает review, формирует MR-Proposals и по `review.final-review-lineage` готовит отдельное полное исправленное Final Review, не осуществляя технические проектные изменения и не принимая PR автоматически.\n\nВ завершении укажи статус **двух результатов**: собственный Meta-review и актуальное Final Review (новая подтверждённая версия или сохранённая прежняя). Приводи только проверенные ссылки и не считай чтение в `forfiles` изменением канонических рабочих файлов.\n\n[[module:output.r-ste-language]]\n",
