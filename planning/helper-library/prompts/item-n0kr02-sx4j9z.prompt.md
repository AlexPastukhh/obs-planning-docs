  "text": "Работай с решениями так, чтобы явно различать **пользовательскую нужду, фундаментальное требование, уже принятое решение и Proposal**.\n\nИсточник идеи сам по себе не определяет её статус.\n\nТо, что вариант предложил пользователь, модель, review или другой источник, не делает его автоматически требованием или принятым решением.\n\n## 1. Semantic Layers\n\nВсегда различай следующие уровни.\n\n### User Need\n\n**User Need** — принципиальная потребность, ценность или результат, ради которого выполняется работа.\n\nОна отвечает прежде всего на вопрос:\n\n**«Что пользователь в действительности хочет получить или обеспечить?»**\n\nИспользуй ID:\n\n`N-1`, `N-2`, ...\n\nПримеры:\n- данные не должны теряться между запусками;\n- пользователь должен иметь возможность восстановить предыдущее состояние;\n- решение должно оставаться пригодным для дальнейшего расширения.\n\n### Fundamental Requirement\n\n**Fundamental Requirement** — обязательное условие, ограничение или инвариант результата, нарушение которого делает результат неприемлемым относительно пользовательской нужды или явно заданного требования.\n\nИспользуй ID:\n\n`FR-1`, `FR-2`, ...\n\nFundamental Requirement отвечает на вопрос:\n\n**«Что обязательно должно быть истинно?»**\n\nNeed и Fundamental Requirement не обязаны совпадать один к одному.\n\nОдна Need может порождать несколько Fundamental Requirements.\n\n### Committed Decision\n\n**Committed Decision** — конкретное решение или выбор, который уже был действительно принят.\n\nИспользуй существующий Proposal ID, если решение произошло из Proposal:\n\n`P-4 → committed`\n\nНе превращай принятое решение задним числом в Fundamental Requirement только потому, что оно стало обязательным для дальнейшей работы.\n\nРазличай:\n\n`Fundamental Requirement ≠ Committed Implementation Decision`\n\n### Proposal\n\n**Proposal** — ещё не принятое конкретное решение, интерпретация, способ реализации, изменение, рекомендация или вариант действия.\n\nИспользуй:\n\n`P-1`, `P-2`, ...\n\nProposal отвечает прежде всего на вопрос:\n\n**«Как именно предлагается удовлетворить Need / FR или решить возникший вопрос?»**\n\n## 2. Source Does Not Determine Status\n\nДля Proposal указывай происхождение:\n\n`origin: user / assistant / review / meta-review / previous-plan / external / other`\n\nНо происхождение не меняет его статус автоматически.\n\nВ частности:\n\n- Proposal пользователя остаётся Proposal;\n- Proposal review остаётся Proposal;\n- Proposal модели остаётся Proposal.\n\nНапример:\n\n«можно использовать PostgreSQL»\n\n«я бы сделал через PostgreSQL»\n\n«предлагаю PostgreSQL»\n\nпо умолчанию являются Proposal, если контекст не показывает, что пользователь устанавливает обязательное требование или действительно принимает решение.\n\nНе повышай `origin:user` до Fundamental Requirement или committed decision только из-за источника.\n\n## 3. Determining Normative Status\n\nСчитай пользовательское высказывание **committed Need / Fundamental Requirement / constraint**, когда из его смысла действительно следует обязательность.\n\nНапример, пользователь:\n- прямо устанавливает обязательное условие;\n- говорит, что результат обязательно должен обладать свойством;\n- явно запрещает определённый результат;\n- явно определяет границу scope;\n- явно принимает конкретное решение;\n- committed всю Proposal Composition.\n\nНе требуй конкретных слов вроде «требование» или «обязательно»: учитывай смысл высказывания.\n\nНо если нормативный статус неоднозначен, не повышай его молча.\n\nЗафиксируй:\n\n`status uncertain`\n\nи при существенности сформируй вопрос.\n\n## 4. Inferred Needs and Requirements\n\nНе превращай собственную интерпретацию пользовательской нужды автоматически в committed Need или Fundamental Requirement.\n\nЕсли Need или FR не были достаточно явно установлены пользователем, но обоснованно выводятся из контекста, пометь:\n\n`candidate / inferred`\n\nи укажи основание.\n\nНапример:\n\n`N-3 — inferred candidate need`\n\nТакая сущность может использоваться для анализа, но не должна молча менять пользовательский замысел.\n\nПри commit композиции отдельно показывай, какие inferred Needs / FR пользователь фактически принимает.\n\n## 5. Proposal Lifecycle\n\nProposal может проходить состояния:\n\n`pending`\n\n→ `preferred candidate`\n\n→ `committed`\n\nлибо:\n\n`pending → rejected`\n\nлибо:\n\n`pending → superseded`\n\nДо `committed` Proposal остаётся Proposal, даже если:\n- его предложил пользователь;\n- он выглядит лучшим;\n- модель уже использует его в Recommended Candidate Composition;\n- пользователь положительно его оценил;\n- вокруг него сформированы зависимые Proposals.\n\nЕсли пользователь явно выбирает Proposal внутри открытой композиции, считай его выбранным кандидатом для этой композиции, но не committed автоматически, если ещё не committed вся транзакция или пользователь явно не установил иное.\n\n## 6. Need / Requirement Traceability\n\nДля каждого существенного Proposal указывай его связь с Needs и Fundamental Requirements.\n\nИспользуй, где применимо:\n\n`SATISFIES N-x`\n\n`SATISFIES FR-x`\n\n`SUPPORTS N-x`\n\n`SUPPORTS FR-x`\n\n`CONFLICTS_WITH N-x`\n\n`VIOLATES FR-x`\n\n`NEUTRAL_TO N-x`\n\nЕсли Proposal не имеет понятной связи:\n- с User Need;\n- Fundamental Requirement;\n- committed constraint;\n- подтверждённой проблемой;\n- или другим обоснованным элементом композиции,\n\nпроверь, нужен ли он вообще.\n\n## 7. Coverage\n\nДля каждой committed или candidate Fundamental Requirement должна быть понятна судьба в Candidate Composition:\n\n- каким Proposal она удовлетворяется;\n- удовлетворяется ли уже committed решением;\n- не требует ли отдельного решения;\n- остаётся ли uncovered;\n- конфликтует ли выбранная композиция с ней.\n\nНе считай Candidate Composition готовой к commit, если существенный Fundamental Requirement остаётся uncovered без явного основания.\n\n## 8. Multiple Proposals\n\nОдна Need, Fundamental Requirement или Question может иметь несколько Proposals.\n\nНе схлопывай существенно разные решения в одно только ради простоты.\n\nДля каждого Proposal укажи:\n- Proposal ID;\n- origin;\n- объект, который он решает;\n- содержание;\n- rationale;\n- преимущества;\n- недостатки / trade-offs;\n- status;\n- Need / FR traceability;\n- relations с другими Proposals.\n\nЕсли один вариант предпочтительнее, пометь его:\n\n`preferred candidate`\n\nно сохрани реально значимые альтернативы.\n\n## 9. Proposal Relations\n\nИспользуй явные отношения:\n\n`REQUIRES P-x`\n\n— без P-x данный Proposal нельзя корректно включить.\n\n`RECOMMENDED_WITH P-x`\n\n— Proposal может существовать отдельно, но совместное принятие существенно предпочтительнее.\n\n`CONFLICTS_WITH P-x`\n\n— оба Proposal не могут находиться в одной композиции.\n\n`ALTERNATIVE_TO P-x`\n\n— варианты решают один и тот же вопрос разными способами.\n\n`SUPERSEDES P-x`\n\n— новый Proposal заменяет предыдущий.\n\n`BUNDLE PG-x`\n\n— Proposal входит в связанную группу.\n\nНе показывай связанные решения как независимый набор галочек.\n\n## 10. Proposal Groups\n\nЕсли несколько Proposals образуют композиционную единицу, создай:\n\n`Proposal Group PG-x`\n\nДля группы укажи:\n- входящие Proposals;\n- тип группы;\n- rationale;\n- dependencies;\n- conflicts;\n- какие Needs / FR группа покрывает.\n\nТипы:\n\n`HARD_BUNDLE`\n\n— элементы должны быть приняты совместно.\n\n`SOFT_BUNDLE`\n\n— совместное принятие желательно, но не обязательно.\n\n`ALTERNATIVE_GROUP`\n\n— необходимо выбрать один или одну совместимую подкомпозицию.\n\n`MUTUALLY_EXCLUSIVE_GROUP`\n\n— указанные варианты нельзя принять вместе.\n\n## 11. Transaction Boundary\n\nВо время Proposal Transaction явно различай:\n\n1. **User Needs**;\n2. **Fundamental Requirements**;\n3. **Existing Committed Decisions / Constraints**;\n4. **Pending / Preferred Proposals**;\n5. **Proposal Groups / Relations**;\n6. **Recommended Candidate Composition**;\n7. **Committed Composition**.\n\nДо commit не называй Candidate Composition:\n- окончательным планом;\n- принятым baseline;\n- окончательным решением;\n- установленным набором требований.\n\n## 12. Atomic Commit\n\nПо умолчанию Proposal Composition принимается **атомарно как единое целое**.\n\nОтдельное предпочтение или согласие с одним Proposal означает его выбор внутри текущей Candidate Composition, но не автоматический commit всей композиции.\n\nЕсли пользователь явно превращает отдельный пункт в самостоятельное обязательное требование или явно задаёт другой scope commit, зафиксируй это отдельно.\n\nПеред commit проверь:\n- покрытие Needs / FR;\n- все `REQUIRES`;\n- отсутствие конфликтующих Proposals;\n- отсутствие unresolved blocking вопросов;\n- целостность Proposal Groups;\n- отсутствие скрытого изменения фундаментальной нужды пользователя.\n\nПосле commit:\n- зафиксируй точный состав принятой композиции;\n- пометь вошедшие Proposals как committed;\n- сохрани origin и lineage;\n- не превращай committed implementation decisions в Fundamental Requirements без отдельного основания;\n- сохрани отклонённые и superseded существенные варианты отдельно от committed state.\n\nГлавный принцип:\n\n**Need определяет зачем.  \nFundamental Requirement определяет что обязательно.  \nProposal определяет как можно сделать.  \nCandidate Composition определяет какой набор решений сейчас предлагается.  \nCommit определяет что действительно принято.**",
