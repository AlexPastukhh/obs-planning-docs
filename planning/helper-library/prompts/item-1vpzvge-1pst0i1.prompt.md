Цель — итеративно улучшать Proposal Composition, сохраняя версии, lineage и накопленное знание.\n\n[[module:core.context-interpretation]]\n[[module:core.need-proposal-semantics]]\n[[module:core.scenario-realization]]\n[[module:core.finding-model]]\n[[module:core.finding-explanation]]\n[[module:core.decision-governance]]\n[[module:core.proposal-composition]]\n[[module:core.user-assistance]]\n[[module:evolution.qrp]]\n[[module:output.situational-github-artifacts]]\n\n**Режим результата по умолчанию:** сформируй полноценную `Candidate Revised Composition` как читаемый Markdown. Если пользователь не задал иное место и для этого плана не согласован текущий рабочий owner, опубликуй новый candidate snapshot в `forfiles` по общему модулю и дай проверенную ссылку. Не заменяй старую candidate/committed версию, не меняй настоящие плановые документы и не объявляй новую композицию принятой только из-за публикации. Если есть согласованное место ведения плана, используй его по фактическим полномочиям; лишнюю копию не создавай без запроса.\n\n\n## 1. Resolve Target / Review Chain\n\nУстанови точный target, source version, её `committed/candidate` статус, какие reviews относятся к какой версии и существует ли уже открытая Candidate Revision. Не применяй review к более поздней версии только потому, что она новее.\n\n## 2. Restore Foundation\n\nВосстанови N/FR, Desired Scenario, SRU composition/tree, committed decisions, pending Proposals/Groups/relations и существующий QRP. Не позволяй review молча менять Need/FR/Scenario.\n\n## 3. Version Model\n\nИспользуй различие:\n`V0 committed → R1(review of V0) → V1-candidate → explicit commit → V1 committed → R2 ...`\n\nЕсли два reviews относятся к одной версии, сохраняй это явно (`R1→V0`, `R2→V0`). Candidate revision не является committed version.\n\n## 4. Stable Identity / Per-item Version Provenance\n\nСохраняй stable IDs и parent/child lineage, где сущность остаётся той же. Для содержательно нового альтернативного решения создавай новый `PR-*`. Используй `REVISED_FROM / SUPERSEDES / DERIVED_FROM` там, где это помогает. Для SRU сохраняй parent path и не превращай изменение реализации в молчаливое изменение Scenario.\n\nДля каждого **material tracked item** — Proposal, Proposal Group, SRU, WR/EA (если применимо) и другой существенной части/пункта плана — должно быть видно, в какой версии он появился и когда содержательно менялся. Сохраняй по возможности:\n- canonical ID;\n- `introducedIn`;\n- `lastChangedIn`;\n- `sourceReview / sourceFinding`;\n- `statusInVersion`;\n- relation к предыдущему состоянию.\n\nЕсли существенная часть плана не имеет стабильного ID, но её нужно различать между review iterations, присвой локальный `PI-*` (Plan Item) только для version tracking.\n\nПри material изменении показывай lineage в форме вроде `PR-4@V0 → PR-4@V1-candidate → PR-4@V2-candidate` или эквивалентно. Не нужно полностью копировать неизменившийся текст каждой версии: для unchanged item достаточно стабильного ID и явного `UNCHANGED`.\n\n## 5. Review Findings → Change Work\n\nДля каждого review finding сначала проверь его обоснованность и canonical type `F-P/F-R/F-U/F-O` либо Evidence Gap. Затем установи, что оно требует:\n- изменения существующего Proposal;\n- нового/альтернативного Proposal;\n- изменения relations/group;\n- изменения SRU/parent SRU/Scenario;\n- User Assistance;\n- только изменения disposition/QRP без изменения plan composition.\n\nReview recommendation не становится change автоматически.\n\n## 6. Upstream Findings\n\nЕсли finding относится выше текущего узла — parent SRU, составу SRU, Desired Scenario, Need/FR, scope или staged/full strategy — пометь UPSTREAM, дай повышенный User Review Priority и не продолжай механически пересобирать downstream план, если upstream решение способно его существенно изменить.\n\n## 7. Multiple Remediation / Improvement Proposals\n\nЕсли finding допускает несколько жизнеспособных способов, создай несколько `PR-*`. Для каждого укажи affected findings/N/FR/SRU, impact на Scenario и realization costs, User Review Priority, Decision Autonomy, trade-offs и version introduced. Сохраняй relations/groups.\n\n## 8. QRP Evolution\n\nОбнови Proposal/Group/Composition QRP как представление над canonical Findings. Для каждого material Q/R/P сохрани ссылку на canonical `F-U/F-R/F-P`, target Proposal/Group/Composition и version/review provenance. Покажи новые, resolved, mitigated, invalidated, reopened и still-applicable связи; не создавай вторую независимую запись истины.\n\n## 9. Scenario / SRU Re-check\n\nПосле proposed изменений заново проверь:\n- сохраняется ли Desired Scenario;\n- не стал ли Scenario дешевле/дороже/сложнее для пользователя;\n- не появилась ли лишняя SRU или преждевременная глубина;\n- можно ли сделать меньшую validation/staged версию;\n- как решение влияет на время, усилия, money/resources, maintainability и accumulated complexity, если применимо;\n- не делает ли новая информация часть дальнейшей реализации ненужной.\n\n## 10. Candidate Revised Composition\n\nСобери новую Candidate Revised Composition: retained/revised/new/superseded/rejected Proposals, Groups/relations, SRU changes, unresolved alternatives, unsatisfied dependencies, open QRP, User Assistance и Need/FR coverage. При нескольких существенно разных viable routes покажи alternatives.\n\n## 11. Per-item Lineage / Composition Delta\n\nДля material tracked items покажи version lineage и затем delta: `UNCHANGED / REVISED / ADDED / REMOVED_FROM_CANDIDATE / SUPERSEDED / REJECTED / REOPENED`, previous state, proposed state, source review/finding и rationale. Удаление из current candidate не удаляет историю.\n\nПользователь должен иметь возможность отличить состояние конкретного пункта **до review, после review 1, после review 2 и далее**, даже если итоговая Candidate Composition уже сильно изменилась.\n\n## 12. Transaction / Commit\n\n**Граница операции:** эта команда по умолчанию **предлагает новую Candidate Revision и публикует её для чтения**, но не выполняет semantic commit и не пишет в рабочий owner. Для применения/commit нужны отдельные явные полномочия и проверенная граница транзакции. Не выдавай подтверждение GitHub-публикации в `forfiles` за подтверждение обновления рабочего плана.\n\nПри учёте meta-review сохраняй различие: исходное review (`R1`) и его перепроверка (`MR1`) дают связанные, но не взаимозаменяемые evidence. Укажи соответствующие источники и их версии; не применяй одновременно опровергнутую рекомендацию R1 и исправляющий `MR-PR-*` так, будто обе действительны.\n\nРезультат сначала имеет статус `CANDIDATE REVISION`. Review findings сами по себе не совершают commit. Перед commit проверь N/FR/Scenario coverage, relations/conflicts, hard dependencies, blocking QRP, upstream findings и material costs.\n\nПосле явного commit: `Vx-candidate → Vx committed`; предыдущую committed version и review/QRP history сохрани.\n\n## 13.
