  "text": "Обнови указанный мной план, pre-work baseline или другую явно указанную плановую композицию на основании относящегося к ней review или последовательности reviews.\n\nЦель этой операции — не просто исправить отдельные замечания, а **итеративно улучшать Proposal Composition**, сохраняя:\n- User Needs;\n- Fundamental Requirements;\n- историю версий;\n- Proposal lineage;\n- связи между Proposals;\n- накопленный QRP;\n- происхождение изменений;\n- различие между candidate и committed состоянием.\n\n## 1. Resolve Target\n\nСначала установи:\n- какой именно объект обновляется;\n- какая его версия является входной;\n- committed она или candidate;\n- какое review или цепочка reviews относится именно к этой версии;\n- существуют ли более поздние версии;\n- существует ли уже открытая Candidate Revision.\n\nНе применяй review к другой версии только потому, что она новее.\n\nЕсли связь `review → target version` ненадёжна, явно обозначь неопределённость.\n\n## 2. Restore Semantic Foundation\n\nПеред изменением композиции восстанови:\n\n### User Needs\n`N-*`\n\n### Fundamental Requirements\n`FR-*`\n\n### Existing Committed Decisions\nвключая committed Proposals.\n\n### Existing Proposal Composition\n- pending Proposals;\n- preferred candidates;\n- Proposal Groups;\n- relations;\n- unresolved alternatives.\n\nНе позволяй review молча изменить User Need или Fundamental Requirement.\n\nЕсли review показывает, что Need / FR были неверно интерпретированы, создай отдельный вопрос или candidate correction и явно покажи изменение семантического основания.\n\n## 3. Version Model\n\nРазличай committed и candidate версии.\n\nИспользуй модель:\n\n`V0 — committed version before Review R1`\n\n`R1 — review of V0`\n\n`V1-candidate — proposed revision after R1`\n\nпосле commit:\n\n`V1 — committed`\n\nзатем:\n\n`R2 — review of V1`\n\n`V2-candidate`\n\nи так далее.\n\nЕсли используется другая существующая схема версий, сохраняй её, но обязательно различай:\n- committed state;\n- review;\n- candidate revision.\n\nНе называй candidate revision новой committed-версией до commit.\n\n## 4. Review Target Provenance\n\nДля каждого review зафиксируй:\n\n- Review ID;\n- target version;\n- scope;\n- дату/порядок относительно других review, если известно;\n- существенные ограничения review.\n\nЕсли два reviews относятся к одной версии, не представляй второе как review уже изменённой версии.\n\nНапример:\n\n`R1 → V0`\n\n`R2 → V0`\n\nне равно:\n\n`R1 → V0`\n\n`R2 → V1`\n\n## 5. Stable Identity / Lineage\n\nПо возможности сохраняй стабильные IDs:\n- Needs;\n- Fundamental Requirements;\n- Proposals;\n- Proposal Groups;\n- Questions;\n- QRP items;\n- существенных plan items.\n\nЕсли Proposal уточняется без изменения основной идентичности, сохраняй его ID и добавляй version lineage:\n\n`P-4@V0`\n\n`P-4@V1-candidate`\n\nЕсли появляется действительно новый альтернативный способ решения, создай новый Proposal ID.\n\nИспользуй отношения:\n\n`REVISED_FROM`\n\n`SUPERSEDES`\n\n`DERIVED_FROM`\n\nтам, где они помогают понять эволюцию.\n\nНе выдавай новый вариант за продолжение старого Proposal, если он фактически является другой альтернативой.\n\n## 6. Classify Review Findings\n\nДля каждого существенного review finding сначала определи его тип:\n\n- confirmed problem;\n- uncertainty;\n- risk;\n- question;\n- false positive;\n- invalidated finding;\n- process improvement;\n- user-assistance opportunity;\n- proposal/recommendation from review.\n\nНе превращай рекомендацию review автоматически в изменение плана.\n\nОтдельно реши, требует ли finding:\n- изменения существующего Proposal;\n- нового Proposal;\n- новой альтернативы;\n- изменения Proposal Relation;\n- изменения Proposal Group;\n- изменения порядка/структуры плана;\n- нового вопроса;\n- User Assistance;\n- изменения Need / FR interpretation;\n- только сохранения знания без изменения композиции.\n\n## 7. Findings → Proposal Work\n\nЛюбое существенное изменение плановой композиции сначала оформляй как Proposal.\n\nДаже если review рекомендует конкретное исправление, это остаётся Proposal до commit.\n\nЕсли review предлагает:\n\n«заменить X на Y»\n\nне считай Y автоматически принятым.\n\nСоздай или обнови соответствующий Proposal и покажи, какие Needs / FR и findings он обслуживает.\n\n## 8. Multiple Remediation Proposals\n\nЕсли один finding можно исправить несколькими существенно различающимися способами, создай несколько Proposals.\n\nДля каждого:\n- Proposal ID;\n- origin review;\n- review finding(s), которые он адресует;\n- Needs / FR traceability;\n- содержание;\n- плюсы;\n- минусы;\n- trade-offs;\n- status;\n- relations;\n- version introduced.\n\nНе скрывай альтернативы только потому, что review предложило один конкретный способ исправления.\n\n## 9. Proposal Relations / Groups\n\nПоддерживай:\n\n`REQUIRES`\n\n`RECOMMENDED_WITH`\n\n`CONFLICTS_WITH`\n\n`ALTERNATIVE_TO`\n\n`SUPERSEDES`\n\n`BUNDLE`\n\nи Proposal Groups.\n\nПосле каждого review заново проверь relation graph.\n\nИщи:\n- unsatisfied hard dependency;\n- conflict внутри Candidate Composition;\n- mutually exclusive Proposals;\n- устаревшие relations после изменения Proposal;\n- циклические зависимости, делающие композицию невозможной;\n- Proposal Groups, потерявшие целостность.\n\n## 10. QRP Model\n\nНакапливай **QRP** как знание о жизнеспособности Proposal Composition.\n\nРазличай три уровня QRP:\n\n### Proposal QRP\n\nQRP конкретного `P-x`.\n\n### Proposal Group QRP\n\nQRP взаимодействия внутри `PG-x`.\n\n### Composition QRP\n\nQRP, возникающий только на уровне всей Candidate / Committed Composition.\n\nЭто важно: проблема может отсутствовать в каждом Proposal отдельно, но возникать при их сочетании.\n\n## 11. Q — Questions\n\n`Q` — существенные открытые вопросы.\n\nДля каждого Q укажи:\n- QRP ID;\n- target Proposal / Group / Composition;\n- source review;\n- вопрос;\n- почему он важен;\n- blocking / non-blocking;\n- текущий статус.\n\n## 12. R — Risks\n\n`R` — правдоподобный потенциальный механизм негативного исхода, который ещё не подтверждён как реально проявившаяся проблема.\n\nДля каждого R:\n- QRP ID;\n- target;\n- source;\n- условия проявления;\n- возможное последствие;\n- существенность;\n- возможное mitigation;\n- status.\n\nНе называй Risk подтверждённой Problem без evidence.\n\n## 13. P — Problems\n\n`P` в QRP — подтверждённая проблема Proposal, Group или Composition.\n\nДля каждой:\n- QRP ID;\n- target;\n- source review;\n- что конкретно неверно;\n- evidence / основание;\n- нарушенная Need / FR / constraint;\n- механизм;\n- consequence;\n- status.\n\nНе смешивай QRP Problem с Proposal ID. Используй разные пространства ID, например:\n\n`P-7` — Proposal\n\n`QRP-P-4` — Problem этого Proposal.\n\n## 14. QRP History\n\nНе перезаписывай старый QRP молча.\n\nДля каждого Q/R/P сохраняй историю статуса:\n\n- `open`;\n- `resolved`;\n- `mitigated`;\n- `invalidated`;\n- `superseded`;\n- `still applicable`;\n- `reopened`.\n\nПри изменении статуса укажи:\n- на какой версии;\n- после какого review;\n- почему статус изменился.\n\nНапример:\n\n`QRP-R-2`\n- introduced: R1 / V0\n- mitigated: V1\n- reopened: R3 / V2\n\nЕсли review оказалось ошибочным, сохрани `invalidated`, а не стирай finding из истории.\n\n## 15. Need / FR Coverage Re-check\n\nПосле применения review findings заново проверь:\n\n- покрыты ли все committed Needs;\n- удовлетворены ли Fundamental Requirements;\n- не изменилось ли их значение молча;\n- не появился ли Proposal, конфликтующий с FR;\n- не исчезло ли покрытие из-за удаления или supersede Proposal;\n- не добавило ли review лишнее «требование», которого пользователь не устанавливал.\n\nCandidate Revision не готова к commit, если существенная committed FR остаётся uncovered без явного решения.\n\n## 16. User Assistance\n\nЕсли review показывает, что небольшой вклад пользователя существенно:\n- снимает блокировку;\n- разрешает QRP-Q;\n- снижает QRP-R;\n- позволяет надёжно проверить QRP-P;\n- исключает непропорционально сложный обход,\n\nсформируй конкретный запрос.\n\nНе останавливай независимые части работы.\n\nНе перекладывай на пользователя то, что можно нормально сделать самостоятельно.\n\n## 17. Candidate Revised Composition\n\nСобери новую **Candidate Revised Composition**.\n\nЯвно покажи:\n\n- retained Proposals;\n- revised Proposals;\n- new Proposals;\n- superseded Proposals;\n- rejected Proposals;\n- Proposal Groups;\n- changed relations;\n- unresolved alternatives;\n- unresolved QRP;\n- excluded conflicts;\n- unsatisfied dependencies;\n- User Assistance;\n- Needs / FR coverage.\n\nЕсли существует несколько существенно разных жизнеспособных композиций, покажи несколько Candidate Compositions вместо искусственного выбора одной.\n\n## 18. Composition Delta\n\nСформируй delta относительно исходной версии:\n\n`UNCHANGED`\n\n`REVISED`\n\n`ADDED`\n\n`REMOVED FROM CANDIDATE`\n\n`SUPERSEDED`\n\n`REJECTED`\n\n`REOPENED`\n\nДля каждого существенного изменения укажи:\n- объект;\n- previous state;\n- proposed new state;\n- source review/finding;\n- rationale.\n\nУдаление из актуальной композиции не означает удаление из истории.\n\n## 19. Transaction Semantics\n\nРезультат этой операции сначала является:\n\n**CANDIDATE REVISION**\n\nа не новой committed-версией.\n\nReview findings сами по себе не совершают commit.\n\nДаже очевидное исправление должно оставаться частью Candidate Composition до commit, если оно меняет плановую композицию.\n\nПеред commit проверь:\n- Need / FR coverage;\n- Proposal relations;\n- conflicts;\n- hard dependencies;\n- unresolved blocking QRP;\n- Proposal Groups;\n- scope impact;\n- fundamental user need impact.\n\nПосле явного commit:\n\n`Vx-candidate → Vx committed`\n\nСохрани предыдущую committed version как историю.\n\n## 20. Output\n\nПокажи:\n\n1. Target Plan / Baseline;\n2. Source Committed Version;\n3. Reviews Applied и target version каждого;\n4. User Needs;\n5. Fundamental Requirements;\n6. Existing Committed Decisions;\n7. подтверждённые review findings;\n8. disputed / invalidated findings;\n9. Proposal changes;\n10. Proposal Relations / Groups;\n11. Proposal-level QRP;\n12. Group-level QRP;\n13. Composition-level QRP;\n14. QRP history/status changes;\n15. User Assistance;\n16. Candidate Revised Composition;\n17. существенные alternative compositions;\n18. Need / FR coverage;\n19. Composition Delta;\n20. unresolved decisions;\n21. Candidate Version label;\n22. Transaction Status.\n\nГлавная цель:\n\n**после каждой итерации должно быть видно не только текущее содержание плана, но и эволюцию его Proposal Composition: что было принято, что review обнаружило, какие альтернативы появились, какие QRP накопились, что изменилось между версиями и почему.**",
