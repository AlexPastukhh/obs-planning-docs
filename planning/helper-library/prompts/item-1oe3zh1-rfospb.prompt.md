  "text": "Твоя задача — полноценно забутстрапиться по текущему состоянию проекта OBS Linked Notes из доступного тебе репозитория или приложенного snapshot.\n\nПосле изучения ты должен выдать собственную проверяемую модель того:\n\n1. что Linked Notes представляет собой СЕЙЧАС;\n2. какие semantic Use Cases сейчас существуют;\n3. как они связаны между собой;\n4. как пользовательские сценарии проходят через приложение;\n5. где проходят state / persistence / repository / remote boundaries;\n6. какие конкретные части реализации обеспечивают каждый Use Case;\n7. какими automated tests и manual acceptance это подтверждается;\n8. какие проблемы или незакрытые вопросы есть в самом проекте;\n9. насколько качественно документация позволяет всё это понять.\n\nЭто одновременно:\n\n- system-understanding audit;\n- semantic/use-case audit;\n- implementation traceability audit;\n- documentation-quality audit.\n\nПлохая реализация и плохое описание реализации — разные классы проблем. Всегда разделяй их.\n\nПока ничего в проекте НЕ изменяй.\n\nНе редактируй файлы.\nНе создавай replacement archive.\nНе пиши implementation patch.\nНе предлагай commit/push.\nНе начинай с рекомендаций по улучшению.\n\nСначала изучение, затем диагностический отчёт.\n\n---\n\n# 1. Source-of-truth rules\n\n## 1.1. Используй текущее состояние, а не память\n\nНе опирайся на память о Linked Notes из других разговоров.\n\nНе предполагай:\n\n- текущую версию;\n- количество Use Cases;\n- конкретные `UC-*` IDs;\n- текущие UI surfaces;\n- текущую publication architecture;\n- текущие названия runtime-модулей;\n- текущий roadmap;\n- текущие acceptance statuses.\n\nВсё это должно быть установлено из текущего repo/snapshot.\n\nLinked Notes может существенно изменяться между запусками этого bootstrap prompt.\n\n---\n\n## 1.2. Если приложен snapshot\n\nЕсли в этом сообщении приложен snapshot / ZIP репозитория:\n\n- считай именно его source-of-truth для bootstrap;\n- исследуй его содержимое;\n- не используй GitHub remote, web или другой repository snapshot без моего отдельного указания;\n- не пытайся “освежить” snapshot через remote;\n- не подменяй его более новой версией, которую ты можешь найти где-либо ещё.\n\nЕсли snapshot не содержит commit SHA, это нормально. Не выдумывай его.\n\n---\n\n## 1.3. Если snapshot не приложен\n\nЕсли тебе доступен текущий repository через подключённые инструменты, используй текущий repository.\n\nСначала установи его routing / ownership structure, а уже потом углубляйся в Linked Notes.\n\n---\n\n# 2. Сначала найди authority structure\n\nНе начинай чтение проекта со случайных implementation files.\n\nСначала установи текущую систему ownership.\n\nНайди repository-level routing / planning / documentation rules, которые объясняют:\n\n- где находится current Linked Notes documentation root;\n- где находится semantic authority;\n- где находится Use-Case Registry;\n- где находится Use-Case Registry или эквивалентный semantic router;\n- где описывается current product behavior;\n- где описывается architecture / implementation structure;\n- где находятся repository-facing contracts;\n- где находятся automated tests;\n- где находится manual acceptance;\n- где находится roadmap/future work;\n- какие документы являются legacy/history/compatibility, а не current authority.\n\nИмена и пути файлов могут меняться.\n\nНе предполагай, что конкретный исторический путь всё ещё является current owner.\n\nСледуй текущим ссылкам и ownership declarations самого repository.\n\n---\n\n# 3. Стабильная conceptual model документации\n\nПри чтении исходи из следующего разделения ответственности.\n\nЭто не означает, что каждый слой обязан быть отдельным файлом, но смысловые роли должны быть различимы.\n\n## Semantic Registry\n\nUse-Case Registry является индексом текущих independently useful semantic user outcomes.\n\nОн должен помогать установить:\n\n- какие Use Cases существуют сейчас;\n- их canonical IDs;\n- semantic names;\n- status;\n- trigger/input;\n- successful user result;\n- связь с более подробным semantic description.\n\nRegistry НЕ должен восприниматься как перечень кнопок, APIs или runtime modules.\n\nНайди текущий Linked Notes Use-Case Registry и используй его как основной индекс canonical Use Cases.\n\nНе предполагай заранее количество и названия UC.\n\n---\n\n## Semantic Map\n\nUse-Case Registry или его текущий эквивалент должен раскрывать semantic meaning registry entries:\n\n- trigger;\n- user result;\n- boundary;\n- dependencies;\n- relationships;\n- supporting capabilities;\n- distinction между Use Case и implementation/UI mechanism.\n\nЕсли registry ведёт на semantic map, пройди все canonical links.\n\n---\n\n## Product / behavior documentation\n\nЭти документы отвечают на вопрос:\n\n> Что пользователь реально может сделать и какое observable behavior приложение обещает сейчас?\n\nОни не должны автоматически считаться implementation authority.\n\n---\n\n## Focused feature / repository contracts\n\nДля некоторых Use Cases могут существовать более узкие contracts:\n\n- repository-facing Markdown conventions;\n- metadata formats;\n- marker formats;\n- feature-specific behavioral contracts;\n- durable repository structures.\n\nНайди их через traceability/links, а не по догадке.\n\n---\n\n## Architecture / implementation documentation\n\nЭти документы объясняют:\n\n- runtime layers;\n- module responsibilities;\n- state flow;\n- integration boundaries;\n- build/runtime organization.\n\nПроверяй их по реальному source code.\n\n---\n\n## Source code\n\nSource code является evidence текущей реализации.\n\nНо:\n\nimplementation choice ≠ semantic identity.\n\nНаличие отдельного модуля само по себе не создаёт отдельный Use Case.\n\n---\n\n## Automated tests\n\nTests являются evidence того, что определённые contracts проверяются автоматически.\n\nНо:\n\nunit/integration tests ≠ browser acceptance;\ntests ≠ real remote acceptance;\ntests ≠ production architecture acceptance.\n\n---\n\n## Manual acceptance / checklists\n\nChecklist/manual acceptance должен рассматриваться отдельно от automated evidence.\n\nВсегда различай:\n\n- тест существует;\n- тест проходит;\n- browser flow проверен;\n- real remote integration проверена;\n- production architecture принята.\n\n---\n\n## Roadmap\n\nRoadmap является future/research/planning evidence.\n\nНе используй roadmap как доказательство того, что behavior уже реализован.\n\nЕсли roadmap описывает вопрос, который код уже фактически решил, отметь возможную stale documentation.\n\n---\n\n# 4. Bootstrap reading strategy\n\nНе выдавай итог после чтения пары верхнеуровневых файлов.\n\nПроведи чтение в несколько проходов.\n\n## Pass A — navigation and authority\n\nОпредели:\n\n- documentation root;\n- semantic registry;\n- semantic map;\n- product overview;\n- architecture docs;\n- state docs;\n- focused contracts;\n- tests;\n- checklists;\n- roadmap;\n- known issues.\n\nПострой reading plan.\n\n---\n\n## Pass B — semantic model\n\nНайди все CURRENT canonical Use Cases из Use-Case Registry.\n\nДля КАЖДОГО current Use Case:\n\n1. открой его canonical semantic description;\n2. установи:\n   - trigger/input;\n   - successful user result;\n   - semantic boundary;\n   - dependencies;\n   - related/supporting capabilities;\n3. найди его traceability к более подробным sources.\n\nНе переписывай registry механически — пойми смысл каждого UC.\n\n---\n\n## Pass C — traceability\n\nДля каждого Use Case пройди цепочку настолько глубоко, насколько она существует:\n\nUse-Case Registry\n→ Semantic Map\n→ Product / behavior docs\n→ Focused contract\n→ Primary implementation\n→ Direct automated tests\n→ Manual acceptance\n\nЕсли какого-то слоя нет — зафиксируй это.\n\nЕсли traceability заявлена, но ссылка неверна или evidence не подтверждает claim — зафиксируй это.\n\n---\n\n## Pass D — implementation\n\nРеально открой primary implementation files.\n\nНе ограничивайся documentation summary.\n\nРазберись:\n\n- кто является orchestrator;\n- какие модули владеют domain logic;\n- где local state;\n- где persistent state;\n- где repository interaction;\n- где UI/runtime adapters;\n- где remote boundary;\n- где validation;\n- где errors/conflicts/freshness;\n- где shared infrastructure.\n\nЕсли архитектура изменилась относительно предыдущих версий — описывай только текущую.\n\n---\n\n## Pass E — tests\n\nОткрой основные прямые automated tests для каждого Use Case.\n\nПроверь:\n\n- какие contracts они реально проверяют;\n- какие edge cases покрыты;\n- какие user-visible claims они НЕ доказывают;\n- где tests относятся только к helper/domain logic;\n- где есть integration coverage.\n\n---\n\n## Pass F — manual acceptance / known gaps\n\nПройди manual acceptance/checklist/known issues.\n\nРаздели:\n\n- implemented;\n- automated tested;\n- manually accepted;\n- browser acceptance pending;\n- real remote acceptance pending;\n- roadmap/future only.\n\n---\n\n# 5. Насколько глубоко понимать реализацию\n\nМне не нужен бессмысленный построчный аудит всего repository.\n\nМне нужно достаточно глубокое понимание, чтобы после bootstrap ты мог уверенно обсуждать:\n\n- изменение существующего Use Case;\n- добавление нового Use Case;\n- изменение state flow;\n- изменение publication flow;\n- изменение UI behavior;\n- изменение repository contract;\n- изменение persistence;\n- изменение tests/acceptance;\n- влияние одного изменения на другие UC.\n\nПоэтому разберись в текущих equivalents следующих architectural concerns, если они существуют:\n\n- application/bootstrap/orchestration;\n- UI / surfaces;\n- repository/workspace context;\n- primary content/entity lifecycle;\n- file/repository workspace;\n- local/pending repository state;\n- remote publication;\n- GitHub/API adapter boundary;\n- categories/classification;\n- references/reference-like objects;\n- ordering/list structures;\n- compound/multi-file flows;\n- reader/import/export/diagnostic surfaces;\n- persistence/storage;\n- conflicts/reconciliation;\n- freshness/staleness;\n- validation;\n- errors/action feedback;\n- build/generation;\n- complete verifier/test runner.\n\nЭто conceptual checklist, а НЕ требование найти модули именно с такими именами.\n\nЕсли какая-то из этих областей больше не существует — не придумывай её.\n\nЕсли появились новые крупные области — добавь их в свою модель.\n\n---\n\n# 6. Что выдать после чтения\n\nПосле изучения дай отчёт в следующей структуре.\n\n---\n\n# 6.1. Executive model — что такое Linked Notes сейчас\n\nСвоими словами объясни:\n\n- что это за система;\n- для какого класса задач она существует;\n- какие основные пользовательские результаты объединяет;\n- какова её центральная current architectural/product idea.\n\nНе копируй README почти дословно.\n\nМне нужна твоя синтезированная модель.\n\nНа ключевые утверждения дай ссылки на authoritative files.\n\n---\n\n# 6.2. Current semantic model\n\nПеречисли ВСЕ current canonical Use Cases, которые реально находятся в текущем Use-Case Registry.\n\nФормат для каждого:\n\n`UC ID`\n→ semantic name\n→ trigger/input\n→ successful user result\n→ boundary\n→ dependencies / related UCs\n→ current status\n\nНе используй заранее известный список UC.\n\nЕсли registry изменился — используй новый.\n\n---\n\n# 6.3. Что НЕ является отдельным Use Case\n\nОтдельно перечисли заметные:\n\n- UI actions;\n- buttons;\n- popups;\n- storage mechanisms;\n- transport/API operations;\n- diagnostics;\n- helper capabilities;\n- infrastructure;\n\nкоторые могут выглядеть как отдельные функции, но semantic model сознательно НЕ даёт им отдельный UC ID.\n\nОбъясни, к какому UC или supporting layer они относятся.\n\nЭто важно для понимания semantic granularity проекта.\n\n---\n\n# 6.4. End-to-end user flows\n\nПострой основные end-to-end flows текущего приложения.\n\nНе исходи из старых flow names.\n\nВыведи реальные current chains вроде:\n\ncontext/setup\n→ user operation\n→ local/domain state\n→ review/validation\n→ persistence/publication\n→ resulting durable state\n\nПокажи:\n\n- где один UC вызывает/подготавливает другой;\n- какие UCs являются producers;\n- какие UCs являются publication/durability boundaries;\n- какие workflows остаются special/compound;\n- где есть read-only flows;\n- где есть diagnostic/export flows.\n\n---\n\n# 6.5. State model\n\nОбъясни текущую модель состояния.\n\nРаздели, где применимо:\n\n- ephemeral UI state;\n- local persistent application state;\n- local pending repository state;\n- remote snapshot/cache;\n- repository truth;\n- derived/indexed state;\n- diagnostic/export state.\n\nДля каждой категории объясни:\n\n- где хранится;\n- кто владелец;\n- как она создаётся;\n- как инвалидируется;\n- когда становится durable;\n- как связана с другими слоями.\n\nОсобенно отметь identity/version/base/freshness assumptions, если они существуют.\n\n---\n\n# 6.6. Durability / remote publication architecture\n\nЕсли текущий Linked Notes умеет менять repository/remote state, отдельно объясни current remote-write architecture.\n\nНе предполагай старую схему.\n\nУстанови из текущих docs + code:\n\n- какие user actions только готовят local changes;\n- какие действия реально выполняют remote mutation;\n- существуют ли single-item и batch/snapshot publication;\n- какие API/transport paths используются;\n- есть ли atomicity;\n- есть ли compare-and-set/base/version protection;\n- есть ли verification/readback;\n- что происходит при conflict/failure;\n- сохраняется ли pending state после failure;\n- какие flows обходят generic publisher;\n- какие операции являются compound/multi-file.\n\nНа технические утверждения обязательно ссылайся на source files и tests.\n\n---\n\n# 6.7. Runtime / implementation architecture\n\nПострой текущую карту implementation layers.\n\nНе делай просто длинный список файлов.\n\nПокажи responsibility graph.\n\nНапример, если это подтверждается текущим кодом:\n\nUI\n→ app orchestration\n→ domain/service\n→ local state\n→ repository adapter\n→ remote API\n\nНо не навязывай эту форму, если текущая architecture устроена иначе.\n\nДля каждого крупного module family объясни:\n\n- ответственность;\n- входы;\n- outputs/state mutations;\n- от каких слоёв зависит;\n- какими Use Cases используется.\n\n---\n\n# 6.8. Per-Use-Case traceability\n\nДля КАЖДОГО current canonical UC дай компактный traceability record.\n\nФормат:\n\n## `UC-...`\n\n**Behavior / semantic owner**\n- конкретные docs\n\n**Focused / durable contracts**\n- конкретные files или `none`\n\n**Primary implementation**\n- конкретные source files\n\n**Automated evidence**\n- конкретные test files\n\n**Manual acceptance**\n- конкретные checklist/docs или `none`\n\n**Current acceptance state**\n- что подтверждено;\n- что pending.\n\nНе пиши:\n\n- “source/tests”;\n- “implementation files”;\n- “see docs”.\n\nНазывай конкретные paths.\n\nPrimary implementation означает действительно primary, а не каждый transitive helper.\n\nЕсли список intentionally non-exhaustive — скажи это.\n\n---\n\n# 6.9. Semantic contract vs implementation choice\n\nОтдельно покажи, что в текущем проекте является:\n\n### Semantic/product contract\n\nТо, изменение чего потенциально меняет Use Case.\n\n### Durable/repository contract\n\nТо, что является долгоживущим repository-facing форматом/правилом.\n\n### Current implementation choice\n\nТо, что можно рефакторить без изменения semantic identity.\n\n### Prototype-only mechanism\n\nТо, что существует для текущего prototype, но не должно автоматически считаться долгосрочной architecture.\n\n### Roadmap/future research\n\nТо, что ещё не является current behavior.\n\nЭто разделение особенно важно.\n\n---\n\n# 7. Анализ проблем самого проекта\n\nПроведи отдельный анализ проблем / рисков текущего Linked Notes.\n\nНе смешивай его с documentation-quality audit.\n\nИщи:\n\n- незавершённые Use Cases;\n- частично реализованный behavior;\n- architectural inconsistencies;\n- fragile state boundaries;\n- persistence risks;\n- conflict/freshness risks;\n- remote/publication risks;\n- compound-flow risks;\n- missing validation;\n- недостаточно покрытые critical paths;\n- behavior, подтверждённый unit tests, но не user-flow acceptance;\n- absence of browser acceptance;\n- absence of real remote acceptance;\n- known issues;\n- roadmap decisions;\n- implementation, расходящийся с semantic contract.\n\nДля каждой значимой проблемы:\n\n`Problem`\n→ `Severity: high / medium / low`\n→ `Affected Use Cases`\n→ `Почему это проблема`\n→ `Evidence`\n→ `Fact или inference`\n→ `Что остаётся непроверенным`\n\nНе создавай проблемы ради количества.\n\n“Я бы написал это иначе” не является проблемой проекта.\n\n---\n\n# 8. Documentation-quality audit\n\nТеперь отдельно оцени качество самой документационной системы Linked Notes.\n\nГлавный вопрос:\n\n> Может ли новый разработчик / новый ChatGPT-чат с разумными усилиями восстановить правильную текущую модель системы и добраться от semantic intent до authoritative implementation/test evidence?\n\n---\n\n## 8.1. Authority / ownership\n\nПроверь:\n\n- ясно ли, где находится current Use-Case Registry;\n- ясно ли, где находится semantic map;\n- ясно ли, какой файл владеет каким видом truth;\n- отделён ли current authority от legacy/history;\n- есть ли документы, которые одновременно выглядят owners одного контракта;\n- может ли старый document случайно перехватить routing.\n\n---\n\n## 8.2. Navigation / discoverability\n\nПроверь, можно ли из нормальной entry point документации последовательно найти:\n\nREADME / entry\n→ Use-Case Registry\n→ Use-Case Registry\n→ конкретный UC\n→ behavior docs\n→ focused contract\n→ source\n→ tests\n→ manual acceptance\n\nИщи важные files, для нахождения которых нужно заранее знать имя.\n\nЕсли пришлось использовать repository search, потому что documentation links не довели до важного owner/evidence — отметь это.\n\n---\n\n## 8.3. Use-Case quality\n\nПроверь для каждого UC:\n\n- понятен ли trigger;\n- понятен ли user result;\n- понятен ли boundary;\n- не смешан ли behavior с implementation;\n- не слишком ли UC широкий;\n- не слишком ли мелкий;\n- нет ли двух UC с фактически одним результатом;\n- не отсутствует ли independently useful current capability из registry.\n\nНе меняй registry только из-за вкусового disagreement.\n\nНужен evidence-based semantic audit.\n\n---\n\n## 8.4. Traceability quality\n\nДля каждого UC проверь реальную цепочку:\n\nRegistry\n→ Map\n→ behavior\n→ contract\n→ implementation\n→ tests\n→ manual acceptance.\n\nПроверь:\n\n- ссылки существуют;\n- anchors существуют;\n- ссылка ведёт туда, куда заявлено;\n- source files действительно primary;\n- tests действительно проверяют соответствующий contract;\n- acceptance evidence действительно относится к UC;\n- implementation/test lists не создают ложной видимости полноты;\n- нет расплывчатого shorthand там, где должен быть точный path.\n\n---\n\n## 8.5. Consistency\n\nСравни claims между:\n\n- semantic registry;\n- semantic map;\n- product overview;\n- architecture;\n- state documentation;\n- focused feature docs;\n- durable repository contracts;\n- source;\n- tests;\n- known issues;\n- roadmap;\n- manual checklists;\n- changelog.\n\nНе считай разные abstraction levels противоречием автоматически.\n\nКлассифицируй найденные расхождения.\n\n---\n\n## 8.6. Freshness\n\nИщи stale документацию:\n\n- behavior, который уже изменён;\n- старую architecture;\n- старый owner;\n- старый semantic ID;\n- roadmap question, который код уже решил;\n- устаревший acceptance flow;\n- старые terminology/state assumptions;\n- changelog-only current behavior, не перенесённый в owner.\n\n---\n\n## 8.7. Completeness\n\nИщи current behavior, который:\n\n- есть только в code;\n- есть только в tests;\n- есть только в changelog;\n- нигде нормально не объяснён;\n- имеет UC, но слабое behavior documentation;\n- не имеет traceability;\n- не имеет acceptance route.\n\n---\n\n## 8.8. Duplication / maintenance risk\n\nНайди важные правила, которые описаны в нескольких местах.\n\nРазличай:\n\n- нормальное краткое summary;\n- вредное duplicate authority.\n\nДля значимого duplication укажи:\n\n- какой документ выглядит canonical owner;\n- какие документы лучше должны ссылаться на него;\n- есть ли уже factual drift.\n\n---\n\n## 8.9.
