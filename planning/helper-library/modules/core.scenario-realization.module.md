  "text": "## Scenario / Scenario Realization Units\n\nИспользуй этот слой, когда для задачи осмысленно описать желаемую реальность и путь к ней.\n\n### Desired Scenario\n\nScenario — сравнительно однозначное, **не рекурсивное** описание желаемой реальности: кто/что находится в каком контексте, какие prerequisites и inputs существуют, какой осмысленный путь проходит пользователь/процесс и какой observable outcome должен быть получен.\n\nScenario должен:\n- действительно удовлетворять User Need и Fundamental Requirements;\n- не содержать лишних шагов и затрат без достаточной пользы;\n- учитывать существенные время, усилия, деньги, ожидание, ручную работу и другие применимые costs процесса достижения результата.\n\n### Scenario Realization Composition\n\n`Scenario Realization Composition` — набор, порядок и зависимости top-level `SRU-*`, которые совместно обеспечивают нужные части/переходы Desired Scenario и позволяют получить его итоговый outcome.\n\nScenario можно разделить на осмысленные части или переходы для планирования реализации, но **не превращай сам Scenario в рекурсивное дерево**. Рекурсивно декомпозируется реализация его SRU.\n\nПроверяй, что top-level SRU composition покрывает весь существенный Scenario без лишних единиц, не создаёт ненужного процесса и сохраняет требуемые prerequisites/inputs/outputs между частями Scenario.\n\n### Scenario Realization Unit (SRU)\n\n`SRU-*` — планируемая единица реализации, необходимая для обеспечения определённой части, перехода, capability или состояния Desired Scenario. Это универсальное понятие и не привязано к приложению: SRU может быть возможностью системы, этапом процесса, артефактом, исследованием, процедурой, механизмом, подготовительным действием и т. п.\n\nSRU может существовать сначала только как **planned realization target**: она не обязана быть уже выполненным действием, feature или implementation task.\n\nДля существенной SRU фиксируй, где полезно:\n- Purpose / contribution to Scenario;\n- Preconditions;\n- Inputs;\n- Required capability / behavior / state transition;\n- Outputs / resulting state;\n- downstream use в Scenario;\n- success criteria.\n\n### Recursive Realization\n\nРекурсия находится **в реализации SRU**, а не в самом Scenario. Top-level SRU можно разложить на дочерние SRU реализации, те — на свои под-SRU и далее, пока единицы не станут достаточно конкретными для реализации/исполнения.\n\nСохраняй parent/child lineage. Дочерняя SRU является частью реализации parent SRU, а не новым вложенным Scenario.\n\n### Simplest Sufficient Realization\n\nДля каждой SRU и под-SRU ищи наиболее простой, эффективный и достаточно надёжный способ обеспечить её вклад в Scenario. Не добавляй сложность только ради гипотетического будущего.\n\nОсобенно проверяй:\n- можно ли сделать меньшую/дешёвую validation-версию перед полной;\n- даст ли ранний маленький шаг информацию, способную изменить последующий план;\n- нужна ли текущей/следующей версии вся предлагаемая сложность;\n- как решение влияет на время, усилия, деньги, maintainability и accumulated complexity, если эти измерения применимы;\n- насколько дорого будет отменить или изменить решение позже.\n\n### Upstream Feedback\n\nПри планировании/реализации текущей SRU постоянно проверяй влияние вверх по дереву:\n- finding внутри текущего способа реализации — current-level;\n- finding, меняющий parent SRU, top-level SRU composition, Desired Scenario, Need или FR — upstream.\n\nUpstream finding не исправляй молча локально. Подними его как отдельную находку и пересмотри зависимую downstream composition после его разрешения, если он материален.",
