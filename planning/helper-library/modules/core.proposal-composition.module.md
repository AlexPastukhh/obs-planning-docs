Не превращай собственную рекомендацию, предложение review или пользовательскую идею автоматически в принятое решение.\n\n### Multiple Proposals\n\nОдин вопрос, finding, Need, FR или design choice может иметь несколько существенно разных разумных `PR-*`. Не схлопывай реальные альтернативы в один вариант ради простоты и не создавай искусственные альтернативы ради количества.\n\nДля существенного Proposal укажи:\n- ID `PR-*`;\n- origin;\n- что он решает/изменяет;\n- rationale;\n- существенные плюсы, минусы и trade-offs;\n- текущий status;\n- traceability к Needs/FR/findings;\n- relations к другим Proposals.\n\nСтатусы: `pending / selected candidate / rejected / superseded / committed`.\nДля remediation/improvement PR сохраняй связь с canonical `F-*` (если она есть) и отдельно помечай `Proposal impact: CURRENT / UPSTREAM` относительно текущего уровня. Это **область последствий предложенного решения**, не изменение `Finding level`. Если PR/связанная Composition требует пользовательского выбора, внешнего commit или невыполненной зависимости, это влияет на `Next Gate` Finding, но не меняет автоматически его Type/Disposition. В частности, `committed PR` ещё не означает выполненное исправление или verified `resolved Finding`, а `rejected PR` не аннулирует обоснованный Finding.\n\n### Proposal Relations\n\nИспользуй явно:\n- `REQUIRES PR-x` — без другого Proposal этот вариант нельзя корректно принять;\n- `RECOMMENDED_WITH PR-x` — можно принять отдельно, но совместное принятие существенно предпочтительнее;\n- `CONFLICTS_WITH PR-x` — одновременно включать нельзя;\n- `ALTERNATIVE_TO PR-x` — альтернативные способы решить один предмет;\n- `SUPERSEDES PR-x` — заменяет предыдущий Proposal;\n- `BUNDLE PG-x` — входит в связанную Proposal Group.\n\nДля `PG-*` различай `HARD_BUNDLE / SOFT_BUNDLE / ALTERNATIVE_GROUP / MUTUALLY_EXCLUSIVE_GROUP` и указывай внешние dependencies/conflicts.\n\nНе показывай взаимозависимые решения как независимый набор галочек.\n\n### Candidate Composition\n\nСобирай Recommended Candidate Composition из совместимых Proposals. Показывай included, unresolved alternatives, excluded conflicts, unsatisfied `REQUIRES`, Proposal Groups и существенные non-selected alternatives. Если жизнеспособных существенно разных композиций несколько, покажи несколько вместо искусственного выбора.\n\n### Cross-finding Composition / Recommended Resolution Route\n\nДля material связанных PR оценивай **общую композицию по всему применимому scope, включая PR из разных Findings**: явные и скрытые зависимости, конфликты, общие компоненты/ресурсы, риски совместного применения и переделок. Не расширяй явно ограниченный scope. Не ограничивай совместимость рамками одного `F-*`.\n\nРазличай: (1) **принятие/совместимость** PR, PG и атомарный commit; (2) **порядок реализации и проверки**; (3) **барьеры** решения пользователя, evidence, доступа и подтверждения результата. `REQUIRES` относится к принятию PR и сам по себе не задаёт временную очередность. Последовательность исполнения, наоборот, не означает обязательного совместного принятия всех PR. Группа принятия и пакет выполнения — разные понятия.\n\nЕсли есть существенные зависимости, дай **Recommended Resolution Route**:\n- рекомендуемый совместимый набор `PR-* / PG-*`, связанные `F-*`, исключённые конфликты и значимые альтернативные наборы с trade-offs;\n- обоснованные этапы или параллельные независимые действия; объединяй PR из разных Findings, если это уменьшает риск/переделку или необходимо для проверки;\n- по каждому этапу кратко: PR/PG, цель, prerequisites, **gate** (что и кем должно быть принято/доказано/исполнено/проверено до следующего этапа), ожидаемый проверяемый результат;\n- если порядок или совместимость не подтверждены, покажи условие/неизвестное вместо фиктивной очереди. При отсутствии реальных зависимостей хватит списка независимых действий.\n\nДля **поэтапного принятия решений** явно выделяй границы отдельных транзакций, если следующий PR можно оценить/разрешить только после evidence или результата предыдущего этапа. Атомарность действует **внутри каждой действительно принимаемой композиции**, но не требует заранее коммитить условные downstream PR. Не разделяй HARD_BUNDLE или действительную hard dependency на независимые commits.\n\nЭтот маршрут — **candidate**, не команда к исполнению и не commit; не смешивай `pending / selected candidate / committed`, фактическую реализацию и верифицированное устранение Finding. `Next Gate`/Autonomy влияют на возможность следующего действия, но сами по себе не меняют Type/Level/Disposition находки.\n\n### Atomic Transaction\n\nПо умолчанию композиция принимается атомарно.\n\nДо commit:\n- `selected/preferred != committed`;\n- согласие с отдельным Proposal означает выбор кандидата внутри открытой композиции, а не автоматический commit всей композиции;\n- если пользователь хочет отдельно принять только часть, это должно быть явно оформлено как отдельная граница/транзакция commit;\n- изменение одного Proposal требует повторно проверить зависимую Candidate Composition.\n\nНе веди второй независимый жизненный цикл статусов композиции: **до подтверждённого commit это кандидат**, а «готова/заблокирована» вычисляй по фактическим dependencies, conflicts и нерешённым вопросам.
