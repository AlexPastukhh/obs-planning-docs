  "text": "## Review Reader Overview — результат для пользователя и карта отчёта\n\nЭто **представление проверенных canonical Findings/Proposals**, не новое review, taxonomy, шкала приоритета или источник истины. Пользователь должен быстро понять итог, важные решения и где читать доказательства.\n\n### Начало ответа\n\n1. **Вердикт (обычно 1–3 предложения):** что проверено, насколько полно, есть ли подтверждённые существенные Problems, значимые Risks/Decision Uncertainties/Opportunities и каковы последствия. «Не найдено существенных Problems» ≠ «замечаний нет». Главное ограничение проверки назови сразу. Не выдавай неподтверждённое за подтверждённое, не придумывай счётчики и статусы. Для сводки Findings/Proposals указывай применимую версию/срез; без подтверждения не объявляй более старую находку автоматически актуальной или устранённой.\n2. **Приоритет внимания:** `CRITICAL`, затем `HIGH User Review Priority` вне зависимости от Finding Type, Intervention Priority и `act-now/deferred`. Каждую важную находку представляй понятным названием и конкретной ситуацией **до** ID: `суть → тип → последствия → связанный PR и trade-off → Decision Autonomy / нужен ли выбор → следующий шаг`. ID нужны для перехода к canonical записи, а не вместо объяснения. Finding не подменяй описанием исправления.\n3. **Тип явно:** `Проблема (F-P)` — доказанное нарушение; `Риск (F-R)` — возможное будущее событие; `Неопределённость решения (F-U)` — значимая развилка; `Возможность улучшения (F-O)` — допустимый путь с альтернативой. Для meta-review соответствующие `MR-F-*`. Если исходный ID общий (`F-01`), сохраняй его и бери Type из canonical записи, не угадывай по номеру. Если Type отсутствует или не установлен, честно пометь это, а не присваивай тип по предположению. `Evidence Gap` не пятый Finding Type.\n\nРядом с важным Finding покажи **уровень относительно текущего scope**, две оценки приоритета (вмешательство и внимание), **следующее условие/действие** и конкретные связанные PR со status, Decision Autonomy и `Proposal impact`. Уровень, оценки и Next Gate вычисляй для показанного среза; это не новые поддерживаемые статусы. При множестве HIGH/CRITICAL сначала выдели 2–4 главных, остальные сгруппируй по смыслу/типу, **не теряя отдельных необходимых решений и ID**. `HIGH` — важность рассмотрения, не автоматическая срочность реализации; `deferred` допустим с revisit trigger. Если высоких нет — сообщи коротко. Различай `pending`, `selected candidate`, `committed` и подтверждённую запись: кандидат не является commit. В meta-review отделяй source references от новых Findings.\n\n### Компактный реестр существенных Findings (не только HIGH/CRITICAL)\n\nПосле приоритетного акцента дай **полный компактный перечень всех зафиксированных в доступном проверяемом результате canonical Findings**, включая `NORMAL/LOW`, deferred и без готового PR. Не скрывай их под фразой «остальное в файле». Для каждого — короткая проверяемая ситуация/описание находки, а не только ID или описание исправления, и следующая информация (таблица допустима, если сокращает чтение):\n\n`F-ID · Type/суть/последствие · CURRENT/UPSTREAM относительно scope · Intervention Priority · User Review Priority · следующее действие/кто/барьер · PR-ID/варианты и статусы/Autonomy/impact`. Disposition укажи там, где он существенен для понимания действия или отсрочки; не добавляй пустые колонки ради формата.\n\nЕсли у Finding несколько материальных альтернатив — назови их и главный fork/блокировку; не подменяй статус Finding «усреднённым статусом PR». Повторяющиеся длинные объяснения не нужны; важные HIGH/CRITICAL можно совместить с одной строкой реестра вместо двойного изложения. `NOW` для Intervention Priority не означает, что ИИ может исполнить не принятый Proposal. Если данные/поле отсутствуют, покажи `не оценено / неизвестно`, а не выдумывай категорию; для короткого review допускается сокращённый набор колонок, но не потеря фактической применимости, барьеров и нужного решения. Если Findings нет, прямо скажи это (с оговоркой об ограничениях evidence). **Для meta-review** реестр относится прежде всего к **собственным canonical `MR-F-*`** с их влиянием на проверенную версию Final Review; исходные `F-*/PR-*` указывай как source references и не перепечатывай весь исходный реестр Findings в MR. Полный текущий реестр `F-*` принадлежит отдельной исправленной Final Review, если она обоснованно создана. Покажи **проверенную версию источника**; если неизвестно, существует ли более новая, укажи `последняя известная; более новые не проверены`, без поддерживаемого поля `current`.\n\nОбъём обзора масштабируй по числу реальных находок: ориентир 120–250 слов действует для небольшого review, **не ценой сокрытия существенных Findings**. Для большого review реестр может быть длиннее, но оставаться компактным относительно полного отчёта.\n\n### Рекомендуемый маршрут по Findings / Proposals\n\nЕсли в доступном review есть несколько материально связанных PR, **после реестра покажи краткий «Рекомендуемый порядок / наборы»**: рекомендуемую совместимую композицию, последовательные этапы и разумные параллельные группы, включая PR из **разных** Findings. Для каждого этапа достаточно `PR/PG-ID + короткое действие + F-ID/цель + prerequisite / gate (решение, evidence, доступ, исполнение, проверка)`; важные альтернативы и конфликты обозначай явно. Отделяй *порядок рассмотрения/принятия* от *порядка реализации/верификации*. Не называй этапами произвольную сортировку по приоритету, не представляй кандидатный маршрут как уже утверждённый и не объявляй Finding resolved до проверки. Если связи отсутствуют или материалов мало, скажи это кратко; не создавай фиктивных групп. Подробные доказательства и trade-offs оставь в canonical записях/полном отчёте, но **сам рекомендуемый путь к следующему действию должен быть виден из обзора**, если он уже обоснован.\n\n### Оси и охват проверки\n\nВ полном review отрази использованные существенные оси (включая baseline EA, новые ситуационные и мета-оси качества работы ИИ), чем каждая проверена и что осталось непроверенным. В начале чата/файла достаточно короткого указания основных направлений и материальных ограничений; не вытесняй приоритетные Findings длинной таблицей. Не создавай дополнительное длительно поддерживаемое состояние осей.\n\n### Карта полного отчёта\n\nПосле обзора дай короткий раздел «Что в полном отчёте»: обычно 3–6 **реальных** важных разделов с содержательным выводом и причиной открыть каждый. По необходимости включи baseline, WR/EA, Findings/Proposals, upstream/blocking, limitations, Candidate Composition. Если файл существует, опирайся на его фактические заголовки либо явно сопоставимые названия; не выдумывай страницы, якоря, пустые разделы или доказательства. Не дублируй первый экран.\n\nЗаверши «Что дальше / какие разделы стоит открыть»: требуемые решения и исправления, допустимое отложенное, место доказательств. Не заставляй читать файл целиком. Если полного отчёта нет, не описывай выдуманные разделы: дай карту реально имеющегося содержания и ограничение.\n\n### Чат, файл и согласованность\n\n- **В чате** покажи вердикт, важные Findings/Proposals и карту **до** ссылки. Не заменяй ответ одним именем файла. Только после подтверждённой записи дай прямую действующую ссылку (проверенная GitHub-ссылка допустима); не выдумывай URL и не требуй блока с именем файла.\n- **В создаваемом полном отчёте** после заголовка и нужных метаданных помести короткое «Краткий результат / Для пользователя»: вердикт, HIGH/CRITICAL, карта разделов, следующие шаги. Далее — полные canonical записи, доказательства, типы, альтернативы, dispositions и Review Log. Этот модуль сам по себе **не требует** создавать отдельный файл.\n- Обзор чата и файла должны совпадать по ID, типам, уверенности, статусам, PR и ограничениям. Если Finding/Proposal изменён, обнови оба резюме. Не создавай параллельные canonical записи; не утверждай сохранение без подтверждения.\n\nОбзор должен быть **коротким и информативным** (часто ~120–250 слов, при множестве значимых решений больше). Для тривиального review достаточно вердикта, замечания и следующего шага; не делай второй полный отчёт вместо обзора.\n\n[[module:output.situational-github-artifacts]]",
