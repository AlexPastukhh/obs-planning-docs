  "text": "## Review Record Semantics\n\nДля достаточно сложного review используй стабильные локальные IDs и одну каноническую запись на сущность:\n- `F-P-*` — Problems;\n- `F-R-*` — Risks;\n- `F-U-*` — Decision Uncertainties;\n- `F-O-*` — Improvement Opportunities;\n- `PR-*` — Proposals;\n- `PG-*` — Proposal Groups;\n- `UA-*` — User Assistance;\n- при необходимости отдельные IDs для Evidence Gaps / Review Limitations.\n\nQuestions являются атрибутами соответствующего finding/Proposal, а не отдельной верхнеуровневой taxonomy. Если один предмет фигурирует в нескольких разделах, создай одну canonical record и используй cross-reference; Review Log может компактно повторять ID/status/смысл.\n\nДля finding фиксируй, где существенно: Type, semantic target, CURRENT/UPSTREAM, impact, disposition, User Review Priority, связанные questions/proposals, evidence и limitations.\n\nДля material question/Decision Uncertainty сохраняй `blocking / non-blocking / partially blocking`; при частичной блокировке указывай affected scope/downstream work.\n\n`Deferred` храни как disposition существующей finding/record с причиной и revisit trigger, а не как самостоятельную природу находки. Не демотируй реальную текущую Problem в deferred ради удобства завершения.\n\n### Review-of-review identity\n\nЕсли объектом проверки является **другое review**, сохраняй IDs исходного review неизменными как source references. Не перенумеровывай их и не используй тот же локальный ID для новой находки meta-review.\n\nДля новых собственных сущностей meta-review используй отдельный namespace, например:\n- `MR-F-P-* / MR-F-R-* / MR-F-U-* / MR-F-O-*` — новые findings meta-review;\n- `MR-PR-*` — Proposals, сформированные самим meta-review;\n- `MR-UA-*` — новый User Assistance meta-review, если нужен.\n\nТак должно быть видно, что относится к проверяемому review, а что обнаружено уже при его перепроверке.\n\nНе вводи IDs и cross-references ради формальности в тривиальном review.\n\n### Reader-first обзор результата\n\n[[module:review.reader-overview]]\n\n### Priority-first / Finding-first presentation\n\nФормат вывода должен помогать пользователю принимать решения, а не заставлять собирать смысл из разнесённых разделов. Это правила **представления** поверх canonical records, а не новая taxonomy, шкала приоритетов или изменение семантики committed/pending.\n\n- В начале пользовательского ответа кратко покажи самые важные findings / связанные Proposals с `CRITICAL`, затем `HIGH` User Review Priority, **независимо от Finding Type**. Для каждого укажи ID, суть, что затрагивает, linked PR-варианты (если есть), требуемое следующее действие и необходимость пользовательского выбора. Если значимых HIGH/CRITICAL нет, не создавай их искусственно. `HIGH` означает важность **рассмотрения**, а не обязательное немедленное исполнение: `deferred` остаётся допустимым с причиной и revisit trigger.\n- В подробной части группируй основные записи так, чтобы `CRITICAL/HIGH` не скрывались за порядком `Problem → Risk → Uncertainty → Opportunity`. Для менее приоритетных допустима группировка по Type; тип, относительный уровень, доказательства и dispositions сохраняй явно. Не заменяй содержательную проверку одним рейтингом.\n- **При первом подробном показе каждого существенного Finding показывай непосредственно рядом связанные Proposals**, а не только ссылку на отдалённый список. Связанные вопросы, блокировки и User Assistance тоже ставь рядом с Finding; детализация пропорциональна значимости.\n- Сохраняй **одну canonical record на Finding и Proposal**. Если один Proposal связан с несколькими находками, не создавай независимые копии с разными статусами: дай полную canonical запись в основном месте и содержательные краткие ссылки в остальных. Общая таблица Proposals/Groups может оставаться для индекса, сравнения или Candidate Composition, но не должна быть единственным местом, где можно понять связанные с Finding варианты. Не дублируй длинные описания без пользы.\n- Если у Finding нет осмысленного Proposal (например, вопрос уже resolved или есть только ограничение доказательств), не придумывай его ради шаблона.
