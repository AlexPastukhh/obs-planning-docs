  "text": "## Review Record Semantics\n\nДля достаточно сложного review используй стабильные локальные IDs и одну каноническую запись на сущность:\n- `F-P-*` — Problems;\n- `F-R-*` — Risks;\n- `F-U-*` — Decision Uncertainties;\n- `F-O-*` — Improvement Opportunities;\n- `PR-*` — Proposals;\n- `PG-*` — Proposal Groups;\n- `UA-*` — User Assistance;\n- при необходимости отдельные IDs для Evidence Gaps / Review Limitations.\n\nQuestions являются атрибутами соответствующего finding/Proposal, а не отдельной верхнеуровневой taxonomy. Если один предмет фигурирует в нескольких разделах, создай одну canonical record и используй cross-reference; Review Log может компактно повторять ID/status/смысл.\n\nДля Finding сохраняй evidence, Type, устойчивый semantic target/parent path, impact, обоснованный disposition и ссылки на PR/questions. В текущем отчёте показывай также **вычисляемые относительно scope/даты** `CURRENT/UPSTREAM`, Intervention Priority, User Review Priority, нужное следующее действие/Next Gate и impact/Autonomy PR. Не объявляй эти отображаемые оценки долговременным источником истины и не веди параллельные статусы.\n\nДля material question/Decision Uncertainty сохраняй `blocking / non-blocking / partially blocking`; при частичной блокировке указывай affected scope/downstream work.\n\n`Deferred` храни как disposition существующей finding/record с причиной и revisit trigger, а не как самостоятельную природу находки. Не демотируй реальную текущую Problem в deferred ради удобства завершения.\n\n### Cross-finding traceability / route\n\nДля одного Proposal, влияющего на несколько Findings, сохраняй **одну canonical запись PR** с обратными ссылками на все затронутые F; и наоборот, разные PR из разных F могут образовать общую композицию. Если есть material зависимости/конфликты или необходимая последовательность, проверяй целостность **общего** Recommended Resolution Route из `core.proposal-composition`, а не только независимые рекомендации для каждой находки. В record показывай причины блокировок и нужные действия без нового независимого статуса Finding. В обзоре достаточно компактного маршрута со ссылками на canonical ID; не копируй отдельные PR записи по этапам.\n\n### Review-of-review identity\n\nЕсли объектом проверки является **другое review**, сохраняй IDs исходного review неизменными как source references. Не перенумеровывай их и не используй тот же локальный ID для новой находки meta-review.\n\nДля новых собственных сущностей meta-review используй отдельный namespace, например:\n- `MR-F-P-* / MR-F-R-* / MR-F-U-* / MR-F-O-*` — новые findings meta-review;\n- `MR-PR-*` — Proposals, сформированные самим meta-review;\n- `MR-UA-*` — новый User Assistance meta-review, если нужен.\n\nТак должно быть видно, что относится к проверяемому review, а что обнаружено уже при его перепроверке.\n\nНе вводи IDs и cross-references ради формальности в тривиальном review.\n\n### Представление и завершающая проверка полноты\n\nФормат первого экрана, полный компактный реестр Findings и маршрут совместимых PR определяет `review.reader-overview` ниже; здесь не повторяй эти правила. Каждая сущность имеет одну canonical запись; при первом подробном показе существенного Finding прямо рядом обозначай связанные PR (суть действия, status/Autonomy/impact/ключевой trade-off), вопросы и требуемые решения. Если PR влияет на несколько Findings, полную запись храни один раз, в других местах дай короткие ссылки; если осмысленного PR нет — не выдумывай его. Cross-finding зависимости — в общей композиции.\n\n**Coverage sweep перед выводом (выполняй, а не создавай новое сохраняемое состояние):** сверяй первоначальные и дополненные в процессе `review.verification-axes` с фактическими evidence/выводами; ось без проверки не равна подтверждённому успеху. Затем сопоставь явный target/scope и версию с фактически просмотренными исходниками, задействованными requirements/FR, критическими частями Scenario/SRU и планом/кодом; проверь отсутствие существенных пропусков по четырём Finding Types, Evidence Gaps, upstream, альтернативным PR, конфликтам между разными Findings, авторизации, verification, содержательной полноте обзора и сохранению/ссылкам, если они применимы. Для review-of-review дополнительно сопоставь исходные Finding/PR и требования исходного review с его доказательствами и выводами нового MR. Для репозитория инвентаризируй относящиеся к target файлы и **material связанные места** (вызовы, зависимости, настройки, тесты, документы), а не случайную выборку. При важном пробеле **досмотри соответствующие файлы/разделы или явно назови unverified area и последствия**. Не заявляй `проверено всё`, если не установлена полнота inventory или доступа. Указывай существенные исключённые части scope и причину; не превращай этот sweep в обязательную отдельную таблицу, статус, файл или формальный чеклист ради галочек.\n\n[[module:review.reader-overview]]\n",
