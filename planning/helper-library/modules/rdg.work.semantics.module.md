  "text": "# Семантика Requirements–Decisions\n\nR (Requirement) одновременно выражает требуемый результат и цель; отдельный тип Goal не создавай. Это модель графа, а не разрешение переименовывать Requirement, Need, FR, Desired Scenario, SRU и другие canonical units из действующей методологии. Когда граф ссылается на чужой semantic owner, сохраняй ссылку и не дублируй нормативный текст.\n\nD (Decision) — конкретный выбранный ответ на R в указанном scope. Связь DRIVES: R → D; решение о разбиении вводит дочерние R связью INTRODUCES: D → R_child с parent равным исходной R-драйверу D. Это одновременно план достижения цели (вперёд) и прослеживаемость происхождения (назад). Одно D может отвечать нескольким R, один R может иметь несколько D. Если общий предмет выбора и scope действительно совпадают, не копируй D.\nDERIVES: R → R — содержательное уточнение (не подмена INTRODUCES при планировании). CONTEXT_FOR: C → D — релевантный контекст. Сквозное применение описано отдельным модулем.\nИсходные пользовательские иллюстрации различают **драйвер как общее основание выбора** и конкретное ребро: драйвером могут быть R, Context и используемая часть другого D. Не превращай Context или фрагмент D в фиктивный R. Нынешний `graph-apply.py` формально сохраняет `DRIVES` только R→D и не умеет все связи из иллюстраций; их следует обсуждать/показывать, но не записывать как неподдерживаемые операции.\nНе разлагай R до бесконечности: прямой D без дочерних R допустим. Соседние подцели не задают автоматически последовательность исполнения; календарный план и зависимости выполнения обсуждаются отдельно при необходимости. Делегация одного R в разные Target Modules не создаёт копии R и не означает выполнение.\nProposal/candidate ≠ committed D; решение принято только при явном выборе пользователя или подтверждённой действующей записи полномочия. Различай выбор решения, достаточность ответа, реализацию и верифицированное достижение R. Ни наличие ребра, ни committed D не доказывают, что цель достигнута.\nContext, Proposal, QRPE-вопрос, evidence, alternatives нужны лишь по делу; не превращай их в фиктивные обязательные Units. Изменение контекста запускает оценку влияния, а не автоматическую отмену решения.\n",
