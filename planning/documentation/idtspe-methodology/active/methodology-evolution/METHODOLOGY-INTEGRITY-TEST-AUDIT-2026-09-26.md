# Methodology Integrity Test Audit — 2026-09-26

Status: historical audit of the v44 test surface. Its proposed parser/fixture/generator rewrite was superseded by [`ON-DEMAND-RELATION-AUDITS-DECISION-2026-09-26.md`](ON-DEMAND-RELATION-AUDITS-DECISION-2026-09-26.md). **The manual decision is not yet implemented.** This audit is not runtime methodology authority.

Status: historical audit of the former hard-test architecture. Its recommendations to retain or expand methodology integrity tests were superseded by the on-demand audit decision and subsequent retirement. Paths and test names below describe the older snapshot, not current files.

Purpose: record the earlier audit of methodology-facing automated tests together with `UC-IDTSPE-MAINTAIN-METHODOLOGY-INTEGRITY-TESTS`, `TESTING.METHODOLOGY-INTEGRITY` and the Methodology Integrity Test Maintenance Process. The earlier proposed disposition below is provenance only.

This audit was prompted by the relation-projection question:

```text
canonical declaration
→ parser / resolver
→ derived relation graph / map / Helper projection
→ tests
```

The critical question is not only whether the final map matches current repository bytes. The parser/resolver that *discovers* attachments, dependencies, owners and bootstrap references must itself be independently proved against controlled fixtures so the producer and test oracle cannot share the same unnoticed bug.

## 1. Scope Reviewed

Repository test surface reviewed:

```text
planning/documentation/tools/tampermonkey/chat-command-palette/tests/
```

All 31 `*.test.mjs` files were scanned. The current standard suite contains 341 tests.

The methodology-integrity owners reviewed were:

- `TESTING.METHODOLOGY-INTEGRITY` / `METHODOLOGY-INTEGRITY-TESTING-CONTRACT.md`;
- `IDTSPE.METHODOLOGY-INTEGRITY-TEST-MAINTENANCE` / `METHODOLOGY-INTEGRITY-TEST-MAINTENANCE.use-case-process.md`;
- `LENS-ATTACHMENT-MAP-INTEGRITY.md`;

- current shared test support in `tests/support/methodology-integrity.mjs`.

The audit also checked whether Attachment/Dependency maps are currently generated by production code. They are **not** currently generated artifacts. They are committed Markdown projections that are manually maintained and checked for parity by tests. Planning Helper currently exposes commands for checking those maps, but it does not yet derive and render the owner relation graph described in `ME-002`.

That distinction matters:

```text
CURRENT
canonical declarations
→ test-local parsers
→ compare against manually maintained Markdown maps

FUTURE DESIRED
canonical declarations
→ verified production relation adapters
→ relation graph
   ├─ generated/maintained map projection
   └─ Helper owner-relations view
```

If maps later become fully generated from the same production parser, exact `source → generated map` equality alone will no longer prove that the parser understood the declarations correctly. Independent fixture tests become mandatory.

## 2. Executive Findings

### Finding A — the low-level resolver is tested; the relation parsers are not

`tests/support/methodology-integrity.mjs` already has useful independent tests for:

- exact-case repository paths;
- Markdown/explicit anchor resolution;
- Responsibility ID + path owner identity;
- canonical-owner anchor versus command read-entrypoint behavior;
- multi-Responsibility files where one Responsibility must not use another Responsibility's canonical anchor.

This is good and should remain.

However, the parsers that discover the actual typed relations are still implemented directly inside integration tests:

```text
Lens Attachments parser
  → lens-attachment-map-integrity.test.mjs
  → methodology-reference-integrity.test.mjs

Semantic Owner Dependency parser
  → tm-lens-dependency-map-integrity.test.mjs
  → methodology-reference-integrity.test.mjs

Bootstrap declaration parser
  → methodology-bootstrap-integrity.test.mjs
```

The attachment and dependency parsers are duplicated. They are not production/shared semantic adapters and they do not have independent fixture/oracle tests for every supported declaration form.

**Required rewrite:** extract typed relation adapters and test them directly with controlled fixture files whose expected relations are written independently of the parser.

### Finding B — correlated-error protection exists in the Contract, but is not fully realized

`TESTING.METHODOLOGY-INTEGRITY` already says:

```text
shared parser/resolver
→ focused contract tests/fixtures
→ positive supported forms
→ negative malformed/wrong-target forms
```

and the Process says to test a changed shared parser/resolver directly before using it as an oracle.

That is directionally correct, but it is still too easy to satisfy with a shallow resolver fixture while leaving the semantic relation parsers unproved.

The Contract/Process should explicitly distinguish:

```text
1. syntax/parser contract proof
2. repository-wide structural/reference proof
3. projection freshness/parity proof
4. architecture/review lint
```

and explicitly say that a map generator and a test that both consume the same parser do **not** independently prove that parser.

### Finding C — large legacy regression files still act as partial second authorities

The largest example is:

```text
methodology-semantic-parity.test.mjs
49 tests
254 match/doesNotMatch assertions
```

It already contains a warning that it mixes structural and semantic/prose guards. That warning is accurate.

The file contains many useful historical regressions, but a large fraction currently hard-fail on exact phrases, current semantic decisions or local prose structure rather than on machine-declared invariants. Such guards can create both:

```text
Escape Risk
→ parser/invariant changes in an untested form and test stays green

Refactor Risk
→ semantic meaning remains valid but wording/layout changes and test fails
```

These should be reviewed one by one and classified, not mass-deleted.

### Finding D — several explicit frozen counts still violate the intended contract

Examples found:

```text
methodology-semantic-parity.test.mjs
  active SDS Target Modules === 14
  active SDS Lenses === 8

unit-checkpoint-contract.test.mjs
  current Target Modules === 33

semantic-navigation.test.mjs
  several exact current inventory counts such as 21 / 8 / 11 / 16 / 41

examples-and-core-aliases.test.mjs
  copied docs === 38
  copied owner files === 14
```

Not every count is automatically wrong. A historical frozen snapshot may intentionally have a fixed manifest. But current methodology inventory counts should normally be derived from the registry/manifest that owns the inventory rather than restated in tests.

### Finding E — bootstrap integrity is structurally good but its parser needs fixtures

`methodology-bootstrap-integrity.test.mjs` avoids hard-coding the current profile count and exact bootstrap read-set size. That is good.

However it contains test-local parsers for:

- numbered read-set links;
- installed profile registry rows;
- responsibility-map rows;
- compact Semantic Owner Dependency rows.

The `compactDependencies()` helper recognizes only the compact dependency syntax. A semantically equivalent rewrite of a profile bootstrap dependency into another globally supported structured form could therefore become a false failure or be invisible to the wrong parser layer.

**Required rewrite:** bootstrap should use a typed dependency adapter with fixtures, plus a bootstrap-specific parser fixture for declared read sets/profile registry rows.

### Finding F — map parity tests are useful today, but their role changes if maps become generated

Today both maps are committed Markdown files maintained as projections, so these checks are meaningful:

```text
canonical Unit declarations == committed Attachment Map
canonical Semantic Owner Dependencies == committed Dependency Map
```

If we later change to:

```text
canonical declarations
→ production parser
→ generator
→ committed/generated map
```

then a test that computes expected relations with the same parser and compares them to the generated map primarily proves **artifact freshness/serialization**, not parser correctness.

At that point correctness must be split:

```text
fixture/oracle tests
→ prove parser semantics

repository integration tests
→ prove all current declarations resolve/validate

generated artifact check
→ prove committed map bytes are current
```

### Finding G — command ownerRef testing is currently one of the strongest areas

The current stack already has several useful independent layers:

- codec tests for `ownerRefs` shape/round-trip/invalid role/path/anchor data;
- shared owner identity fixtures;
- source-command inventory coverage;
- repository-wide canonical identity resolution;
- a multi-owner-file control that prevents a command read-entrypoint from masquerading as another Responsibility's canonical anchor.

This area should be consolidated rather than redesigned from scratch.

The main rewrite need is to remove older duplicate weaker checks, such as checking only "file exists + explicit anchor exists" when the stronger canonical identity test already exists.

## 3. Required Test Architecture

The methodology test architecture should be made explicit as four layers.

### Layer 1 — Parser / Resolver Contract Fixtures

Purpose: prove that production relation readers correctly interpret controlled source files.

These tests must use deliberately small fixture files with independently authored expected results.

Suggested fixture surface:

```text
tests/fixtures/methodology-relations/
├── owners/
│   ├── TM-A.md
│   ├── TM-B.md
│   ├── LENS-X.md
│   ├── LENS-Y.md
│   └── MULTI-RESPONSIBILITY.md
├── bootstrap/
│   ├── PROFILE-REGISTRY.md
│   ├── PROFILE-A-README.md
│   └── RESPONSIBILITY-MAP.md
├── expected/
│   ├── attachments.json
│   ├── dependencies.json
│   ├── owners.json
│   └── bootstrap.json
└── invalid/
    ├── attachment-wrong-anchor.md
    ├── dependency-markdown-only.md
    ├── dependency-duplicate.md
    ├── dependency-malformed.md
    ├── dependency-wrong-owner.md
    └── bootstrap-duplicate-read.md
```

The exact directory names are not authority; the important requirement is independence of the oracle.

Minimum positive attachment fixture:

```text
TM-A / RU-A1
  REQUIRED [CLOSING] → LENS-X
  TRIGGERED          → LENS-Y
```

Expected relation set is written independently:

```text
TM-A / RU-A1 → LENS-X / REQUIRED / CLOSING
TM-A / RU-A1 → LENS-Y / TRIGGERED
```

Minimum positive dependency fixture must cover every supported syntax:

```text
compact
structured multiline
compact structured with semicolons
```

All three should normalize to typed edge objects.

Minimum negative controls:

```text
ordinary Markdown link only
→ produces no Semantic Owner Dependency

wrong Responsibility ID + path
→ FAIL

wrong canonical anchor
→ FAIL

broken path / exact-case mismatch
→ FAIL

duplicate exact dependency declaration
→ FAIL

attachment Lens ID does not match linked canonical Lens
→ FAIL

same Lens both REQUIRED and TRIGGERED for one Unit
→ FAIL

command ownerRef uses another Responsibility's canonical anchor in same file
→ FAIL
```

### Layer 2 — Repository Structural Integrity

Purpose: apply the already-proved parsers/resolvers to the real repository.

Examples:

```text
all current command ownerRefs resolve canonically
all current Unit Lens Attachments resolve to registered canonical Lenses
all current Semantic Owner Dependencies resolve to valid canonical owners
all declared bootstrap reads resolve with exact case and no duplicate declared target
```

These tests should not manually repeat current expected inventories unless the inventory owner itself declares the exact list.

### Layer 3 — Projection / Consumer Freshness

Purpose: prove a consumer reflects canonical declarations.

Examples:

```text
Attachment relation set == committed Attachment Map relation set
Dependency relation set == committed Dependency Map relation set
canonical registry inventory == generated semantic-components seed
command source definitions == generated commands seed
```

If a projection becomes generated from the same verified parser, this layer becomes primarily a generated-artifact freshness/serialization check.

### Layer 4 — Architecture / Semantic Review

Purpose: catch smells or regressions that are valuable but not objectively derivable from a structured authority.

Examples:

```text
bootstrap may be too heavy
particular wording appears to re-own another owner's semantics
current prose seems to imply an unwanted architecture
an example may be conceptually misleading despite resolving structurally
```

These should be one of:

- review/Lens findings;
- a non-hard lint if useful;
- promoted to a hard test only after a canonical machine-checkable declaration is introduced.

## 5. Audit of the Use Case / Contract / Process

### 5.1 `TESTING.METHODOLOGY-INTEGRITY` — KEEP, BUT STRENGTHEN

The Contract is fundamentally aligned with the desired architecture. It already owns:

- authority direction;
- no-second-authority principle;
- typed relation separation;
- owner identity + relation-specific anchor policy;
- shared resolver with separate semantic adapters;
- parser/oracle independence;
- positive/negative controls;
- Escape Risk / Refactor Risk;
- failure diagnostics;
- change protocol.

Required additions/clarifications:

#### A. Define four proof layers explicitly

Add a canonical distinction between:

```text
PARSER_CONTRACT
REPOSITORY_INTEGRITY
PROJECTION_FRESHNESS
ARCHITECTURE_LINT
```

A test should state which layer it belongs to.

#### B. Define independent fixture oracle

Strengthen `Parser / Oracle Independence` to require:

```text
fixture source files authored independently
+ explicit expected typed relation objects
+ production parser under test
```

The expected relation set must not be produced by the parser being tested.

#### C. Address generated maps explicitly

Add:

```text
If producer and parity test consume the same verified parser,
projection equality proves freshness/serialization, not parser semantics.
Parser semantics must already be proved by independent fixtures.
```

#### D. Require one canonical parser per typed declaration syntax

Avoid duplicated regex implementations across tests.

```text
one dependency parser
one attachment parser
one bootstrap declaration parser/adaptor
one command ownerRef codec/parser
```

Different relation semantics remain separate even if they share low-level path/anchor mechanics.

#### E. Add stale-parser controls

For each parser family, require controls where a supported syntax form is changed without changing meaning. Example:

```text
compact dependency
→ structured multiline equivalent
→ same typed edge result
```

This reduces Refactor Risk.

### 5.2 Methodology Integrity Test Maintenance Process — KEEP, BUT MAKE PARSER STEP MANDATORY

Current step 11 says:

```text
If a shared parser/resolver is introduced or changed, test that parser/resolver directly before using it as a projection oracle.
```

Rewrite it more strongly:

```text
For every typed relation whose parser is used by a hard repository/projection test,
identify its parser contract evidence.
If none exists, create fixture/oracle proof before treating repository parity as sufficient evidence.
```

Add an explicit decision:

```text
Is the projection manually maintained or generated from the same parser?
```

because this changes what projection parity proves.

Add an explicit anti-duplication step:

```text
Search for another parser/regex for the same declaration form.
Consolidate or justify the duplication before adding a third implementation.
```

### 5.3 `UC-IDTSPE-MAINTAIN-METHODOLOGY-INTEGRITY-TESTS` — KEEP, BUT EXPAND RESULT/BOUNDARY

The Use Case is correctly scoped and should remain the orchestration owner.

Add to Situation:

```text
a relation parser is about to feed more than one consumer
(map + Helper, map + integrity test, generator + UI, etc.)
```

Add to Result:

```text
parser contract evidence identified/provided
+ relation adapter reuse plan
+ producer/oracle independence assessment
```

Strengthen the boundary from:

```text
use one untested parser as both producer and unquestioned oracle
```

into:

```text
do not count producer-vs-consumer equality as parser correctness when both sides depend on the same parser
```

This is the exact failure mode raised by the current audit.

## 6. Concrete Rewrite Plan

### Phase 1 — build typed parser fixture foundation

Create production/shared relation readers outside individual tests, for example:

```text
src/methodology-relations.js
```

or another appropriately bounded module.

Do **not** create one untyped global graph API. Export separate adapters such as:

```text
parseSemanticOwnerDependencies(...)
parseUnitLensAttachments(...)
parseBootstrapReadSet(...)
resolveCanonicalOwnerReference(...)
```

The exact API names are implementation detail.

Add independent fixture tests first.

### Phase 2 — migrate repository integrity tests to verified adapters

Rewrite:

```text
methodology-reference-integrity.test.mjs
lens-attachment-map-integrity.test.mjs
tm-lens-dependency-map-integrity.test.mjs
methodology-bootstrap-integrity.test.mjs
```

so they consume verified typed adapters rather than private regex parsers.

### Phase 3 — decide map materialization model

Make an explicit design decision:

```text
A. committed manually maintained projection
or
B. generated committed artifact
or
C. runtime-only generated view with no committed map body
```

If A:

- keep exact canonical→map parity tests.

If B:

- generator uses verified parser;
- build/check ensures committed bytes are current;
- parser fixture tests remain the correctness oracle.

If C:

- no map parity file test is needed;
- test relation graph + rendering behavior instead.

Do not accidentally mix all three models.

### Phase 4 — implement Helper owner-relations from the same verified adapters

Desired flow:

```text
command.ownerRefs
→ direct owner list
→ resolve each owner
→ derive owner-specific typed relations
   ├─ Semantic Owner Dependencies
   └─ Unit ↔ Lens attachment projection
→ render in Helper
```

Direct owners, inherited command owners and owner-internal relations remain visibly separate.

UI tests should primarily use fixture relation graphs; repository integration tests separately prove that current repository declarations can produce such graphs.

### Phase 5 — triage legacy semantic regression suites

Review in this order:

```text
1. methodology-semantic-parity.test.mjs
2. semantic-navigation.test.mjs
3. command-composition.test.mjs
4. unit-checkpoint-contract.test.mjs
5. examples-and-core-aliases.test.mjs
```

For each assertion classify:

```text
KEEP HARD
DERIVE
FIXTURE-TEST
LINT / REVIEW
REMOVE / SUPERSEDED
```

Do not modify a test until its protected canonical decision is identified.

### Phase 6 — rewrite UC/Contract/Process wording

After the parser architecture is concrete, update the Contract/Process/UC with the stronger layer/oracle rules above so documentation describes actual practice rather than an aspirational pattern.
