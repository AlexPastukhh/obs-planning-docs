# Review Strategy And Coverage Contract

Status: active peer review-control owner
Purpose: define how a bounded semantic subject is reviewed through materially distinct checks, how repeated review passes avoid avoidable repetition, and how changes invalidate only affected review coverage.

<a id="review-strategy-coverage"></a>
## 1. Core Definition

Responsibility ID: `REVIEW.STRATEGY-COVERAGE`

```text
Review Strategy
= current-basis plan for materially useful review checks
  over one bounded semantic review scope.

Review Coverage
= review-control state describing which semantic surfaces
  have been checked through which review perspectives/operations,
  on which basis, and which cells remain partial/stale/unreviewed.
```

This responsibility controls **review coverage**, not semantic product/planning meaning. It does not create a new Shell port, Target kind, Finding lifecycle, Need lifecycle or persistence requirement.

> Semantic Owner Dependencies
> - `CONTEXTUALIZES` [`AI Reviewability`](AI-OUTPUT-REVIEWABILITY.md) — `AI.REVIEWABILITY`
> - `CONTEXTUALIZES` [`Lens Model`](../idtspe-core/lenses/LENS-MODEL.md#lens-meta-model) — `LENS.META-MODEL`
> - `CONTEXTUALIZES` [`Finding Disposition`](../idtspe-core/resolution/findings/FINDING-DISPOSITION.md#resolution-finding-disposition) — `RESOLUTION.FINDING-DISPOSITION`
> - `CONTEXTUALIZES` [`Proposal / Decision Lifecycle`](../idtspe-core/resolution/proposal-decision/PROPOSAL-AND-DECISION-LIFECYCLE.md#resolution-proposal-decision-lifecycle) — `RESOLUTION.PROPOSAL-DECISION-LIFECYCLE`

## 2. Coverage Unit

Review coverage is not merely `file checked`.

Use the smallest useful review cell:

```text
semantic subject / surface
× review perspective (often a Lens or validator)
× review operation
× relevant basis
→ coverage status
```

The same file or semantic subject may therefore be reviewed several times when the checks are materially different. Lens operations such as `ANALYZE`, `CHECK`, `REFINE` and `CHALLENGE` are distinct when they ask materially different questions. Review planning therefore selects executable Lens review cells as `(Lens Model, Analysis Surface, Operation, relevant basis)` applications rather than selecting only Lens IDs.

A file path/anchor may identify where a semantic surface is represented, but file count alone is not review coverage.

<a id="review-coverage-record"></a>
## 2A. Review Coverage Record

A review that may need continuation or recheck MUST keep one coherent **Review Coverage Record** in current Work Context. This is review-control state, not a new planning State kind.

Use proportionally:

```text
Review Coverage Record
  Review Subject Reference
  Review Scope
  Current Basis
  Previous Basis / Prior Record reference, when available

  Coverage Cells[]
    Semantic Surface Reference
    Perspective / Lens / Validator
    Review Operation
    Basis Reference
    Status
    Coverage Origin
      EXECUTED_THIS_PASS | REUSED_FROM_PRIOR
    Reused From, when reused
    Reuse Justification, when reused
    Evidence / inspected source references
    Finding references, when any
    Invalidated By, when stale

  Changes Since Prior Pass
  Newly Exposed Surfaces
  Remaining Material Coverage
  Scope Escalations / Blockers
```

The record provides the continuity needed by `idtspe.review.recheck`. Do not infer a previous review from memory when no reliable prior record/evidence exists. If no trustworthy prior coverage can be resolved, recheck falls back to an initial current-basis review over the bounded subject rather than inventing a review delta.

The record is transient by default. P-14 Persistence may preserve the same record when it must survive a session boundary, support a long multi-pass review, or has independent durable value. P-02 may record events that update the record, but P-02 remains execution trace rather than the coverage authority.

<a id="review-coverage-working-context"></a>
## 2B. Pre-Execution Review Coverage Working Context

Command composition may know the requested review mode before any dependency semantic action executes. `idtspe.review`, `tmcmd.review.findings` and current-basis specialized reviews such as `idtspe.review_consistency` contribute `REVIEW_COVERAGE_MODE=CURRENT_BASIS`; `idtspe.review.recheck` contributes `REVIEW_COVERAGE_MODE=LOCAL_AFFECTED_RECHECK`. After the command DAG is fully expanded and pre-execution contributions are collected, but **before** P-12 Validation or P-06 Lens dependency actions execute, establish/refresh one bounded Review Coverage working context:

```text
Review Subject / Scope
+ current Basis
+ REVIEW_COVERAGE_MODE
+ trustworthy prior Review Coverage Record when applicable
→ candidate review obligations/intents + reusable prior coverage + blockers
→ P-12 resolves validator checks from that context
→ P-06 alone resolves Lens applicability/supported operation and forms executable selected Lens Applications
```

An existing Pre-Update Plan may be explicitly selected as the bounded Review Subject under `CURRENT_BASIS`, with affected owners/dependencies and destination facts included when materially relevant. Review does not create that plan as an ordered prerequisite. If the requested subject does not exist, report the missing basis rather than deriving cells from an imagined plan. `CURRENT_BASIS` derives current-basis review obligations/intents and reusable coverage candidates. `LOCAL_AFFECTED_RECHECK` compares prior/current basis and derives stale, partial, invalidated, newly exposed or previously blocked obligations while preserving only justified reusable prior coverage. These are coverage requirements, not a second Lens-applicability decision: `REVIEW.STRATEGY-COVERAGE` may request a perspective/operation, but P-06 Lens Meta-Model/Registry owns whether a Lens applies, which supported operation is valid, and the final selected `(Lens Model, Analysis Surface, Operation, basis)` application. If no trustworthy prior record exists, `LOCAL_AFFECTED_RECHECK` falls back to initial current-basis derivation instead of inventing a delta. When both modes are contributed for the same bounded review context, the effective mode is normalized to `LOCAL_AFFECTED_RECHECK`; do not execute parallel current-basis and recheck contexts for the same subject.

This working context is not another command, Shell port, persisted state kind or second review lifecycle. It is the pre-execution form of the same Review Coverage Record owned here. The selected review command's later own action completes Finding Disposition, coverage update and the final coverage self-check after its Validation/Lens dependencies have produced results.

## 3. Current-Pass Completeness

A review pass MUST NOT intentionally defer a materially applicable check merely to create another pass. It should catch everything materially reviewable from the current basis rather than reserving obvious checks for later.

```text
subject available
+ required basis available
+ materially applicable validator/Lens available
+ authority to inspect is available
→ perform the useful check in the current pass
```

Normative invariant:

> A review MUST NOT intentionally defer a materially applicable review perspective when the bounded subject, required basis, applicable validator/Lens and authority are already available.

A later pass is not progress merely because the same material was reread.

Quality target:

> A repeat pass on an unchanged basis should not normally discover a material omission that was already visible to an applicable review perspective in the previous pass.

This is a proportional obligation, not a requirement to apply every Lens indiscriminately.

## 4. Why Repeated Review Can Still Be Necessary

A later pass is justified when the review basis materially changes, including:

```text
accepted correction/change after a Finding
new or changed Evidence
previous blocker resolved
newly exposed semantic surface/dependency
changed upstream/downstream meaning
previous PARTIAL/STALE coverage
materially changed review scope
```

Changes can reveal issues that were not visible before the change. This is normal and is not proof that the prior pass was deficient.

## 5. Coverage Status

Use proportionally:

```text
PLANNED
IN_PROGRESS
CHECKED_NO_FINDING
FINDING
PARTIAL
BLOCKED
NOT_APPLICABLE
STALE
RECHECK_REQUIRED
```

Do not synthesize a numeric quality score.

`FINDING` means a Finding Candidate was produced; the Finding lifecycle itself remains owned by Finding Disposition.

## 6. Change Impact / Invalidation

After a material change, do not blindly reset all coverage.

```text
change
→ identify affected semantic surfaces
→ invalidate only coverage cells whose basis/subject materially changed
→ discover newly exposed surfaces
→ preserve unchanged trustworthy cells as reusable
→ mark affected/new cells for recheck
```

A previously checked cell may remain reusable when its semantic basis and relevant dependencies did not change. Reuse MUST preserve provenance: do not present a prior check as if it executed in the current pass.

<a id="review-coverage-provenance"></a>
### 6A. Coverage Provenance

Coverage status and coverage origin are separate dimensions. `CHECKED_NO_FINDING` or `FINDING` describes the semantic review result; it does not say whether the check executed in this pass.

```text
Coverage Origin
  EXECUTED_THIS_PASS
  REUSED_FROM_PRIOR
```

For `REUSED_FROM_PRIOR`, record the prior cell/basis plus a concise reuse justification showing why the relevant semantic surface and dependencies remain unchanged. A recheck summary should distinguish executed cells from reused cells rather than counting both as newly checked. When reuse cannot be justified from reliable coverage/basis evidence, mark the cell for recheck instead of inferring reuse from memory.

## 7. Recheck Scope

Default repeated review is `LOCAL_AFFECTED`:

```text
changed subjects
+ invalidated coverage cells
+ newly exposed surfaces
+ materially affected dependents
```

Useful scope meanings:

```text
LOCAL
→ current semantic subject only

LOCAL_AFFECTED
→ current subject plus materially affected/new semantic surfaces

BOUNDED_SCOPE
→ an explicitly bounded Target/component/file-set/family

GLOBAL
→ all applicable methodology/repository surfaces
```

Do not silently escalate a local review into global review. When a local finding reveals a materially broader owner/blast radius, either record/defer the broader consequence or obtain USER intent to expand scope when that choice matters.

## 8. Review Lifecycle Boundary

A normal `idtspe.review` is a complete review operation:

```text
refresh strategy/coverage
→ Validation / selected `(Lens, Analysis Surface, Operation, basis)` applications
→ material Finding Candidates
→ Finding Disposition
→ linked Proposal formation/refinement for every material Finding
→ coverage update
```

There is no normal complete `idtspe.review` mode that leaves its own produced Finding Candidates undispositioned. If disposition is blocked/deferred, record that explicitly.

Finding discovery/diagnosis and Proposal formation are distinct actions. Optional Core [`TM-REVIEW-FINDINGS`](../idtspe-core/target-modules/TM-REVIEW-FINDINGS.md) may present an independently useful diagnostic Target result, and [`TM-PROPOSAL-WORKUP`](../idtspe-core/target-modules/TM-PROPOSAL-WORKUP.md) may present a separate bounded candidate-resolution result. Neither Target is mandatory for a complete review: the canonical Finding/Proposal lifecycles still execute directly when a separate Target would add no value. An intermediate Finding analysis with pending Proposal handoffs is not a completed review pass.

Need Candidate collection is **not** a mandatory review stage. Needs are grounded wanted outcomes from USER/Source context and use their own collection/disposition owners. A review may incidentally notice uncollected USER/Source wanted outcome, but it routes that to Need collection rather than treating Need intake as review output by default.

Before a review pass completes, perform a **coverage self-check** against the current Review Subject, Scope and Basis:

```text
re-evaluate applicable validators / review perspectives
→ confirm every materially applicable current-basis cell is
   checked, validly reusable, NOT_APPLICABLE or explicitly BLOCKED
→ distinguish EXECUTED_THIS_PASS from REUSED_FROM_PRIOR coverage
   and preserve reuse basis/justification
→ confirm all produced material Finding Candidates reached Finding Disposition
→ check each material Finding's Priority/RE and upstream/downstream/USER-attention
   conclusions have the required rationale and inspectable basis; keep unsupported
   conclusions explicitly unresolved rather than claiming no impact or no new decision
→ confirm each material Finding has a linked Proposal in the current Work Context,
   including BLOCKED_BY_REVALIDATION state when RE-3 is unresolved
→ record remaining material coverage / blockers / scope escalation
→ only then complete the pass
```

This self-check is intrinsic to Review Strategy/Coverage and is not a separate command or responsibility.

The diagnostic obligation is owned by [Finding classification and consequence basis](../idtspe-core/resolution/findings/FINDING-DISPOSITION.md#finding-classification-consequence-basis); candidate-specific consequences and evidence-backed no-new-selection claims are owned by [Proposal Semantic Change Impact Review](../idtspe-core/resolution/proposal-decision/PROPOSAL-AND-DECISION-LIFECYCLE.md#proposal-semantic-change-impact-review). Reused conclusions retain their checked basis; a label or link without its supporting connection is not sufficient review evidence.

<a id="review-recheck-operation"></a>
## 9. Recheck Operation

`idtspe.review.recheck` uses the same review lifecycle but selects work from prior/current coverage:

```text
previous coverage + current basis
→ stale / partial / invalidated / newly exposed / previously blocked cells
→ targeted validation / selected Lens Application checks
→ Finding Candidates
→ Finding Disposition
→ linked Proposal formation/refinement for every material Finding
→ coverage update
```

It does not need to execute `idtspe.review` first and therefore must not model `idtspe.review` as a prerequisite include.

At recheck start, compare the resolved prior Review Coverage Record/basis with the current basis and expose the delta explicitly. Recheck targets stale/partial/invalidated/newly exposed/previously blocked material first; trustworthy unchanged cells remain reusable with `REUSED_FROM_PRIOR` provenance, prior-cell/basis reference and reuse justification. When no reliable prior record exists, perform initial current-basis review semantics rather than claiming a prior-vs-current delta.

## 10. P-02 Boundary

```text
P-02 Pass Trace
= what methodology-runtime events actually occurred.

Review Coverage
= what review perspectives over which semantic surfaces are currently covered,
  stale, partial or still needed.
```

The same working trace may record review events, but P-02 is not the authority for review applicability or coverage sufficiency.
