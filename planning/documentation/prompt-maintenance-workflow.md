# Reusable Prompt Maintenance Workflow

Status: active reusable documentation-layer workflow
Scope: create, review or change reusable AI prompts/helper insertions without turning them into semantic authority.

## Core Rule

```text
reusable prompt
→ interaction/bootstrap/diagnostic aid
→ points to current semantic/navigation owners
≠ source of truth for changing repository meaning
```

If a readable current owner contradicts the prompt, the current owner wins. Prefer stable conceptual guidance plus current route discovery over copied exhaustive semantic bodies.

## Profiles

- **router / tiny bootstrap** — establishes where to start and what current owners to resolve; keep output compact.
- **light bootstrap** — adds a concise assimilation summary and a compact checked-files report.
- **deep bootstrap / audit** — may require Files Checked with depth, reconstructed current semantic model, contradictions/ambiguities, Questions/Risks/Problems, not-verified gaps and confidence.
- **verification extension** — is inserted after another bootstrap to deepen semantic-entry/implementation/evidence verification without duplicating that full block inside every bootstrap prompt.
- **utility snippet** — exact reusable text/code payload; do not force bootstrap/audit reporting onto it.

## Bootstrap Evidence Contract

For light/deep bootstrap prompts, require only evidence useful to the selected depth. Deep bootstrap/audit should normally report:

```text
Files Checked
→ exact path
→ FULL / DEEP / TARGETED / ROUTING ONLY
→ why it was read / what it established

Material Documentation Findings
→ real contradiction / stale route / ambiguous owner / missing required owner

Planning Concerns / Q/R/P
→ use the shared Concern model for material active/residual findings; group one-resolution-surface concerns; do not manufacture issues or invent user-owned preferences

Not Read / Not Verified
→ material evidence gaps

Confidence
→ distinguish checked fact from inference
```

Ordinary planning commands do not inherit this reporting contract merely because prompts use it.

## Creation / Review Algorithm

1. identify prompt purpose/profile and intended user result;
2. resolve the applicable semantic registry/owner route that the prompt must navigate;
3. keep semantic authority in those owners and make the prompt explicitly defer to them;
4. include only stable conceptual guidance needed to navigate/read correctly;
5. choose output/evidence requirements proportionally to the profile;
6. for bootstrap/audit prompts, require checked-source/depth reporting and material Planning Concerns/Q/R/P when useful;
7. avoid frozen exhaustive path/UC/Scenario lists when current repository routing can resolve them;
8. validate the helper-library document and exact insertion text;
9. check the active prompt library for byte-identical or materially duplicate records under different IDs/titles; byte-identical active prompt bodies must have one current record, while materially overlapping but non-identical prompts may coexist only when their distinct interaction purpose is explicit;
10. review for stale terminology, conflicting ownership, invented permissions and unnecessary duplicated methodology.

## Do Not

- do not make a prompt the semantic owner of a UC, Scenario, workflow or command;
- do not let a prompt grant command/repository permissions;
- do not require every bootstrap to enumerate every semantic entry; use a composable verification extension when deep per-entry traceability is desired;
- do not keep byte-identical active prompt copies under different IDs/titles;
- do not invent problems just to fill an audit section.
